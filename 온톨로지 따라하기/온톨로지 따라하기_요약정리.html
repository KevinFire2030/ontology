이 책에서 가져갈 한 가지 관점

온톨로지는 새로운 DB의 이름이 아니라, 업무의 개념과 관계를 일관되게 해석하기 위한 명시적인 정의다.

책은 가상 구독 서비스의 고객·계약·환불 질문으로 시작한다. 문서 검색만 하는 구성에 정형 조회, 규칙 처리, 의미 모델, 일부 그래프 탐색을 차례로 붙여 어디에서 개선이 생기는지 살핀다. 뒤의 구성이 무조건 더 좋은 단계라는 뜻은 아니다. 업무에 필요한 수준에서 멈추는 것이 핵심이다.

배우는 것

  • 오답의 원인과 적절한 개선 수단 구분
  • 업무 용어·조건·시점·근거의 모델링
  • PostgreSQL 기반 구현과 구성별 비교

이 문서가 보장하지 않는 것

  • 예제 프로그램의 재실행·운영 안전성 검증
  • 다른 모델·도메인에서의 성능 보장

01 · 문제 진단

RAG의 오답을 네 가지로 나누기

유형진단 질문우선 해결책
R · 검색문서에는 답이 있지만 필요한 조항을 못 가져왔는가?조항 단위 분할, 메타데이터, 키워드·벡터 결합
D · 데이터문서가 아니라 고객·결제·사용량 데이터가 필요한가?식별자 연결과 SQL 사실 조회
M · 의미같은 표현을 다르게 해석하거나 조항 관계를 놓쳤는가?표준 용어, 혼동 개념, 준용·대체 관계
K · 규칙조건·예외·시점·계산을 제대로 적용하지 못했는가?필수 입력 검사와 결정적 규칙 평가

한 질문에는 여러 원인이 겹칠 수 있다. 먼저 정답 조항을 직접 주어도 틀리는지 확인한 뒤, 사실 조회와 조건 판단의 누락을 살핀다. 검색 문제를 모델링 문제로, 계산 문제를 온톨로지 문제로 잘못 분류하면 도입 비용만 늘어난다.

사례를 읽을 때 구분할 것

  • 해지 ≠ 환불: 다음 갱신을 멈추는 요청과 이미 낸 돈을 돌려받는 요청은 서로 다른 업무다.
  • 규정 설명 ≠ 고객별 판단: 환불 조건을 설명할 수 있어도 해당 고객의 결제·사용량을 모르면 금액을 확정할 수 없다.
  • 미확인 ≠ 0: 사용량 기록이 없다는 사실만으로 미사용이라고 단정하면 안 된다.
  • 유창한 답 ≠ 정답: 핵심어 채점도 표현 차이와 우연한 단어 포함에 영향을 받으므로 사람이 오류 사례를 함께 살핀다.

책의 최초 기본 RAG 채점 10/30과 최종 재채점 11/30은 구분해야 한다. 비교 표에는 모든 구성에 동일하게 정비한 채점 기준을 적용한 값을 사용한다.

02 · 개념 구분

온톨로지·스키마·그래프는 같은 말이 아니다

구분핵심 역할환불 사례에 대입하면
DB 스키마저장 구조와 데이터 정합성결제 금액·고객 키·날짜를 어떤 열에 담을지
온톨로지 / 의미 모델개념·관계·제약의 해석 기준해지와 환불의 구분, ‘미사용’의 의미, 규정 간 준용
지식 그래프개체와 연결에 관한 구체적 사실어떤 결제가 어떤 구독·규정과 연결되는지
RAG검색한 근거를 활용하는 답변 생성환불 조항을 찾아 답변의 문맥으로 제공
GraphRAG그래프를 활용한 검색·문맥 구성직접 검색한 문서 외에 관련 연결을 탐색
PostgreSQL로도 시작할 수 있다.

합의한 개념·관계·근거를 테이블과 API로 관리하면 관계형 DB 안에서도 의미 모델을 구현할 수 있다. 그래프 DB나 OWL부터 도입할 필요는 없다.

책에서 팔란티어 사례를 통해 강조하는 것은 객체·행동·근거를 연결하는 설계 관점이다. 특정 제품을 따라 구매하거나 플랫폼 전체를 재현하라는 의미는 아니다. 또한 이 책의 실험은 자동 추출 GraphRAG와의 직접 비교가 아니므로 우열을 결론 낼 수 없다.

03 · 실습 준비

설치보다 먼저 비교 가능한 기준선을 만든다

Python·PostgreSQL·pgvector·LLM 호출 환경을 준비하고, 같은 문서와 질문을 여러 구성에 반복 적용한다. 기본 RAG를 건너뛰면 무엇이 개선됐는지 비교할 기준이 없어진다.

환경 확인

  • Python 환경과 DB 연결을 먼저 검사
  • 내장 DB와 Docker 경로를 구분
  • 모델 ID·임베딩 차원·설정 기록
  • 실제 실행 버전과 의존성 고정

평가 준비

  • 질문별 정답·근거·보류 조건 정의
  • 금액 오차와 금지 표현 기준 고정
  • 토큰·시간·호출 수를 함께 수집
  • 모든 구성을 같은 채점기로 재평가

책의 내장 경로 실측 환경은 PostgreSQL 16.2·pgvector 0.6.2로 보고되어 있다. 별도 Docker 검수 환경과 동일한 것으로 섞지 않는다. 이 요약 작성에서는 환경 설치나 예제 벤치마크를 실행하지 않았다.

실습 명령의 적용 범위

예제 코드는 이 보관 저장소에 포함되어 있지 않다. 원저자의 별도 예제 저장소와 해당 장의 절차를 확인해야 한다. 테이블을 재생성하는 적재 스크립트는 운영 DB가 아닌 격리된 실습 DB에서 다룬다.

04 · 최소 의미 모델

회사 전체가 아니라 답해야 할 질문부터 모델링한다

  1. 질문·정답·근거·데이터를 함께 읽는다. 명사·동사만 뽑지 말고, 정답을 바꾸는 인증 만료·요청자 역할·갱신 조건도 찾는다.
  2. 개념·속성·규칙을 분리한다. 결제는 개념, 결제 금액은 속성, 조건별 환불 계산은 규칙으로 구분한다.
  3. 표현과 의미를 연결한다. 동의 표현, 혼동하기 쉬운 별개 개념, 상하위 종류를 서로 다른 항목으로 관리한다.
  4. 관계에 방향과 근거를 붙인다. 인용·준용·대체를 모두 막연한 관련 관계로 합치지 않는다.
  5. LLM 제안은 사람이 검토한다. 중복 개념, 뒤집힌 관계, 불필요한 파생값 저장을 걸러낸다.
사전 항목무엇을 기록하는가주의점
surface_forms하나의 개념을 가리키는 여러 표현맥락 없는 ‘취소’를 무조건 환불로 대응시키지 않기
confusable_with혼동되지만 다른 개념해지·환불·결제 취소를 동의어로 합치지 않기
subtypes종류의 상하위 관계모든 조건 조합을 하위 클래스로 늘리지 않기

4장 최종 YAML의 개념 항목 17개와 6장 DB 적재 보고의 concepts 22개는 집계 대상을 확인해야 하는 수치다. 하나의 일관된 ‘전체 개념 수’로 합치지 않는다. 구조 검사 통과 또한 업무 의미의 완전성을 증명하지 않는다.

05 · 조건·시간·근거

정의한 의미를 실제 판단과 연결하기

① 조건과 필수 정보

조건이 성립하는지와 판단에 필요한 정보가 있는지는 다른 검사다. when과 requires를 구분하고, 먼저 적용할 규칙과 특정 예외가 덮어쓰는 규칙을 명시한다.

② 사건과 규정의 시간

결제일·요청일·시행일을 별개로 취급한다. 최신 규정을 무조건 적용하지 말고 기본 판과 예외적 판 선택을 구분한다. 필요한 경우 구판·신판 결과를 계산해 비교한다.

③ 설명 가능한 근거

문서명만 저장하지 말고 판·조항 ID까지 연결한다. 준용의 출발 조항과 실제 적용 조항, 판 비교에 사용한 근거가 추적되어야 한다.

④ 보류와 다음 질문

미확인·해당 없음·확인 완료를 구분한다. 부족한 사실, 요청 의미의 모호함, 권한 제한을 같은 이유로 뭉개지 말고 필요한 다음 행동을 알려준다.

네 층의 책임을 섞지 않는다

의미 모델은 무엇을 뜻하는지, 규칙은 어떤 결론을 내릴지, DB 제약은 어떤 값이 저장 가능한지, 에이전트 제어는 어떤 행동을 허용할지 맡는다. 환불 불가 판정이 나와도 요청 이력은 저장해야 하므로 업무상 거절과 DB 삽입 금지를 혼동하면 안 된다.

실습의 시간은 고정된 가상 기준이다.

사례 기준일은 2025-09-08이다. 책 속 ‘오늘’이나 ‘현재 규정’을 이 요약을 읽는 날짜의 실제 규정으로 해석하지 않는다.

06 · PostgreSQL 구현

운영 테이블과 의미 관계 테이블을 함께 쓴다

저장 영역대상설계 포인트
운영 데이터고객·구독·결제·사용량고정 구조와 계산에 유리한 전용 테이블 유지
의미 정의개념·용어·관계 유형공통 ID와 명시적 해석 기준 사용
규정과 근거판·조·항·유효기간현재 판뿐 아니라 과거 적용 조건 보존
조항 연결인용·준용·대체·정의 링크방향과 대상 유형을 검증
검색용 파생 데이터본문 임베딩본문 변경 시 갱신; 사실 조회·규칙과 분리
  • 종료일이 비어 있다고 현재 유효한 것은 아니다. 시작일도 기준일과 비교해야 한다.
  • 현재 주기와 과거 사건을 구분한다. 어떤 결제와 사용량을 조인하는지 먼저 확정한다.
  • API는 업무 질문 중심으로 만든다. 적용 판·고객 상태·용어 후보·근거 관계를 반환하고 최종 규칙 판정과 책임을 나눈다.
  • 관계 추가는 파일 한 줄로 끝나지 않을 수 있다. 스키마의 허용 관계, 참조 검사와 조회 API도 함께 바뀐다.

저자는 조항 108개·링크 56개 등의 적재를 보고한다. 이 수치는 소규모 예제의 규모이지 대규모 성능 증거가 아니다. 기간 겹침 검사와 이력 관리의 일부는 추가 설계·별도 검수 항목으로 구분되어 있다.

07 · 응답 파이프라인

LLM이 설명하고, 코드가 사실과 계산을 통제한다

질문 구조화

요청 종류, 고객 ID, 시점, 역할과 모호한 조건을 추출한다. 이 단계에서 결론을 내리지 않는다.

처리 경로 선택

고객별 판단은 SQL·규칙 경로로, 일반 규정 설명은 검색 경로로 보낸다.

사실 조회·규칙 평가

필수 정보, 판 선택, 예외와 계산을 코드로 처리하고 보류 상태를 남긴다.

근거 확장

직접 조항뿐 아니라 준용·정의·비교 판의 근거를 수집한다.

컨텍스트 구성

필요한 개념, 조회 사실, 계산 설명과 근거만 묶어 전달한다.

응답 생성

결론·적용 조건·근거·미확인 사항을 설명한다. 계산 결과를 임의로 뒤집지 않게 한다.

설계 의도와 구현 완료는 다르다.

책의 예제에는 생성문을 자동 반려하는 완성된 후검증기가 없다. 금액·보류·인용 형식은 프롬프트에 의존하는 부분이 남아 있다. 고객 미발견·빈 검색 결과도 안전한 보류로 일관되게 차단되지 않는다.

학습 메모의 보완 제안: 정상 질문·데이터 없음·근거 없음·추가 확인 필요를 분리하고, 생성 뒤 금액·판정 상태·근거 ID를 구조화된 결과와 대조한다. 승인권자 설명과 실제 승인 실행도 별도 권한 경계로 유지한다. 이는 책에 모두 구현되어 있다는 주장이 아니다.

08 · 구성 비교

무엇을 추가했을 때 어떤 문제가 풀렸는가

책은 같은 질문 30개에 다섯 구성을 적용한다. 아래 표는 부록 B가 보고한 3회 실행 집계이며, 이번 요약 작업에서 재실행한 결과가 아니다.

구성추가되는 요소해석 포인트
1 · 기본 RAG작은 문서 청크의 벡터 검색정형 사실 조회 없는 기준선
2 · 검색 개선조항 단위·메타데이터·하이브리드 검색·유효 판 필터검색 개선 효과를 먼저 분리
3 · SQL·규칙고객 데이터 조회와 현재 규정 기준 계산데이터·규칙의 효과를 의미 모델과 분리
4 · 의미 모델용어 기반 분석·판 비교·관계 확장·보류·응답 제어여러 요소가 함께 바뀐 복합 구성
5 · 그래프 탐색영향 범위 질문에 재귀 CTE전용 그래프 DB로 이전한 구성이 아님
각 행의 호출·토큰·시간은 질문 30개를 처리한 한 회분의 평균. 안정 정답은 3회 모두 맞힌 문항 수.
구성평균 정답 /30안정 정답호출토큰시간
1 · 기본 RAG11.0113042,667103초

결과에서 읽을 것

  • 가장 큰 평균 개선은 SQL·규칙을 추가한 구간이다. 이 개선을 전부 온톨로지의 효과로 계산하면 안 된다.
  • 구성 4는 더 많은 질문을 풀지만 호출·토큰·시간도 늘어난다. 정확도뿐 아니라 유지보수와 검수 부담까지 도입 판단에 포함한다.
  • 구성 5의 평균 정답은 구성 4와 같다. 그래프를 붙인 사실 자체가 전체 성능 향상을 보장하지 않는다.
  • 평균과 안정성은 다른 지표다. 평균 점수가 같아도 매번 맞히는 문항은 다를 수 있다. 낮은 구성의 불안정성이 적다고 더 신뢰할 수 있는 것도 아니다.

실험 해석의 한계

  1. 문서 6종·질문 30개의 작은 가상 사례이며 의미 충돌과 시점 문제를 의도적으로 포함한다.
  2. 구성 4는 의미 모델 외에도 분석 호출·프롬프트·근거 범위·행동 제어가 함께 달라졌다. 제거 실험이 없어 단일 요소의 인과효과를 분리할 수 없다.
  3. 채점 기준을 한 번 정비한 뒤 모든 구성을 재채점했다. 핵심어 기반 점수는 판단의 정확성과 표현의 일치를 완전히 분리하지 못한다.
  4. 회차별 코드 커밋과 실행 시각이 기록되지 않았다. 구성 5의 Q30은 분석 정규식 보완 전후가 섞여 있어 통제된 그래프 효과로 읽을 수 없다.

저장소보다 질문의 탐색 형태를 먼저 본다

PostgreSQL에 남을 조건

내 프로젝트에 적용하는 최소 실행 순서

아래는 책의 논지를 바탕으로 이 요약에서 재구성한 체크리스트다. 원저자의 별도 검증 결과가 아니라 프로젝트 계획을 위한 제안이다.

  1. 질문과 정답 기준부터 고정한다.
    반복 업무 질문, 필요한 사실, 적용 근거, 보류가 정답인 경우를 기록한다.
  2. 기본 검색과 데이터·규칙을 먼저 비교한다.
    오답을 R/D/M/K로 분류하고, 검색 개선이나 SQL만으로 해결되는 항목을 분리한다.
  3. 남은 의미 충돌에 최소 모델을 만든다.
    용어 사전, 관계 방향, 규정 판, 예외, 근거 ID를 정리한다.
  4. 원문·모델·DB·응답의 연결을 검사한다.
    결측 보존, 날짜 경계, 기간 겹침, 관계 대상, 계산과 최종 반올림을 테스트한다.
  5. 성능과 유지비를 함께 평가한다.
    같은 채점 기준으로 반복 실행하고 모델·커밋·시간·토큰·호출 수를 남긴다. 필요하면 요소를 하나씩 제거해 기여를 확인한다.
  6. 운영 안전장치와 수정 책임을 정한다.
    빈 결과·데이터 미발견·추가 질문·권한 제한을 명시적으로 처리하고, 변경 시 회귀 평가할 범위를 정한다.
