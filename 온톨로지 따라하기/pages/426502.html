고객 C007이 환불을 요청했습니다. 결제한 지 6일이 지났으니 기간 요건은 충족합니다. 그런데 사용량 테이블에 C007의 이번 주기 기록이 없습니다. 기본 RAG는 여기서 두 가지 오답 중 하나를 냅니다. 기록이 없으니 "사용하지 않았다"고 보고 전액 환불이라고 답하거나, 정보가 없다는 사실을 아예 언급하지 않고 규정 원문만 읊습니다. 정답은 "결론을 보류하고 사용량을 확인한다"입니다(Q19). 이 절은 결론에 필요한 조건 목록을 만들고, 확인되지 않은 조건을 찾아 추가 질문을 만들고, 보류 답변을 형식으로 고정하는 방법을 다룹니다.

결론에 필요한 조건 목록 만들기

05-1에서 규칙의 when 과 requires 를 구분했습니다. when 이 "조건이 참인가"라면 requires 는 "그 조건을 판단할 사실이 확인되었는가"입니다. requires 목록이 바로 결론에 필요한 조건 목록입니다.

목록은 규칙을 만드는 사람이 머리로 짜내는 것이 아니라 업무 문서에서 가져옵니다. 노트클라우드 운영 매뉴얼 1절은 환불 요청을 접수할 때 확인할 정보를 표로 정해 두었고, "하나라도 확인되지 않으면 결론을 내리지 않고 고객에게 확인을 요청한다"고 못 박았습니다. rules.yaml 의 requires 는 이 표를 옮긴 것입니다.

운영 매뉴얼 1절 확인 항목 requires 항목 어느 규칙이 요구하는가 데이터 출처
결제 완료일 paid_at 월간·연간 규칙 전부 payments.csv
결제 주기 billing_cycle 규칙 선택 조건(when) subscriptions.csv
요금제 plan 학생·팀 규칙의 when subscriptions.csv
프로모션 코드 적용 여부 promo_code promo 규칙의 when payments.csv
사용 여부(문서 생성 수, 로그인 횟수) docs_created, logins monthly_full_refund, monthly_no_refund usage.csv
요청자가 팀 관리자인지 requester_role exclude_non_admin_team team_members.csv
계정 정지 여부 account_status exclude_suspended 의 when customers.csv

표에서 어떤 항목은 requires 에 있고 어떤 항목은 when 에만 있습니다. 차이는 "모르면 어떻게 되는가"에 있습니다. billing_cycle 을 모르면 어느 규칙을 적용할지 자체를 정할 수 없으므로 규칙 선택 단계에서 이미 멈춥니다. 반면 docs_created 는 규칙이 선택된 뒤 결론을 좌우하는 사실이므로 requires 에 명시해 두어야 "모른다"를 "아니다"로 오해하지 않습니다.

연간 일할 환불 규칙은 계산에 필요한 값을 requires 에 추가로 요구합니다.

- id: yearly_prorated_refund
  requires: [paid_at, amount, current_period_end, monthly_price]

결제 시각까지 필요한 규칙도 있습니다. 결제 취소(payment_reversal)는 24시간 이내인지 판단해야 하므로 날짜가 아니라 시각(paid_at_time)을 요구합니다.

확인되지 않은 조건 찾기

규칙을 평가할 때 각 requires 항목의 상태를 세 가지로 구분합니다.

상태 뜻 예
known 값이 확인됨 C001의 docs_created = 0
unknown 값을 확인할 수 없음 C007의 사용량 행이 없음
not_applicable 이 요청에는 필요 없음 개인 고객의 requester_role

핵심은 unknown 을 거짓이나 0으로 바꾸지 않는 것입니다. 2-2에서 닫힌 세계 가정(Closed World Assumption)과 열린 세계 가정(Open World Assumption)을 비교했습니다. 관계형 DB는 닫힌 세계라서 행이 없으면 "없다"로 취급합니다. usage 테이블에 C007 행이 없으면 LEFT JOIN 결과는 NULL인데, 여기에 COALESCE를 씌워 0으로 채우면 문서 0건, 로그인 0회가 되고, 그대로 두면 "미사용"이 됩니다. 집계 함수도 마찬가지로 갈립니다. 빈 입력에 대해 COUNT는 0을 돌려주지만 SUM·AVG·MAX 등은 NULL을 돌려주므로, 어떤 함수를 쓰고 NULL을 어떻게 처리하느냐가 곧 판단을 좌우합니다. 온톨로지가 취하는 열린 세계 가정은 "기록되지 않은 것은 모르는 것"입니다. model.yaml 의 has_usage 관계에는 이 점이 적혀 있습니다.

- id: has_usage
  from: Subscription
  to: Usage
  note: 결제 주기마다 하나. 없으면 "미확인"이지 "미사용"이 아니다

구현에서는 두 가지를 구분해야 합니다. "사용량 행이 있고 값이 0"은 known 이고, "사용량 행이 없음"은 unknown 입니다. 6장에서는 LEFT JOIN 결과의 NULL 과 실제 0을 구분해 조회하도록 설계하고, 7장의 규칙 평가기는 NULL 을 만나면 unknown 으로 표시합니다. 이것이 열린 세계 가정을 닫힌 세계인 SQL 위에서 흉내 내는 최소한의 장치입니다.

노트클라우드 질문 세트에서 보류로 끝나야 하는 사례를 보겠습니다.

질문 상황 unknown 항목 이유
Q19 C007 환불 요청, 결제 6일 경과 docs_created, logins usage.csv 에 S007 행이 없음. 미확인은 미사용이 아님
Q04 "어제 결제했는데 취소하고 싶어요" request_type, paid_at_time "취소"가 해지·환불·결제 취소 중 무엇인지, 결제가 24시간 이내인지 시각 확인 필요
Q23 C011 팀의 구성원 팀원K1이 환불 요청 없음(requester_role = member 로 known) 규칙 결론은 "처리 불가", 관리자가 다시 요청해야 하므로 처리가 멈춤

Q04는 정보 부족이 두 겹입니다. 먼저 요청 종류가 정해지지 않았습니다. rules.yaml 의 classify_request 규칙은 requires 에 request_type 하나만 두고, "'취소'라는 말은 해지·환불·결제 취소 중 무엇인지 확인 전에는 판단하지 않는다"고 적었습니다. 4-2의 용어 사전에서 "취소"가 세 개념과 혼동된다고 정리한 것이 여기서 규칙으로 이어집니다. 요청 종류가 결제 취소로 확인되면 다음으로 결제 시각이 필요합니다. "어제"는 날짜이지 시각이 아니므로 24시간 판정을 할 수 없습니다.

Q23은 엄밀히 말하면 unknown 이 없습니다. 요청자 역할이 구성원으로 확인되었고 exclude_non_admin_team 규칙이 "처리 불가, 팀 관리자가 요청해야 함"이라는 결론을 냅니다. 그럼에도 질문 세트가 이 질문을 보류(hold)로 분류한 이유는, 환불 가능 여부에 대한 판단이 아니라 요청 자격에 대한 판단이며, 관리자가 다시 요청하면 처리가 계속되기 때문입니다. 결론이 "환불 여부"가 아니라 "누가 다시 요청해야 하는가"인 답변은 보류 형식으로 내는 것이 상담 흐름에 맞습니다.

추가 질문 생성 규칙

unknown 이 발견되면 사람에게 무엇을 물을지 만들어야 합니다. 이 책은 항목마다 질문 문장을 미리 정해 두는 방식을 씁니다. LLM에게 자유롭게 질문을 만들게 하면 매번 다른 표현이 나오고, 확인할 필요가 없는 것까지 묻기 때문입니다.

unknown 항목 누구에게 질문 문장 확인 수단
request_type 고객 "해지(다음 결제부터 중단), 환불(결제액 반환), 결제 취소(24시간 이내 철회) 중 어느 것을 원하시나요?" 고객 답변
paid_at_time 상담원 "결제 승인 시각을 결제 내역에서 확인해 주세요." 결제 시스템
docs_created, logins 상담원 "해당 결제 주기의 사용량(문서 생성 수, 로그인 횟수)을 조회해 주세요." 사용량 조회
requester_role 상담원 "요청자가 팀 관리자인지 팀 정보에서 확인해 주세요." 팀 정보

질문을 만들 때 규칙은 세 가지입니다.

  1. 결론을 바꿀 수 있는 항목만 묻습니다. 계정이 정지된 고객이라면 사용량을 물을 필요가 없습니다. priority 100 규칙이 먼저 결론을 냈으므로 나머지 requires 는 평가하지 않습니다.
  2. 한 번에 묻습니다. unknown 이 둘이면 두 질문을 한 답변에 모읍니다. Q04처럼 순서가 있는 경우(요청 종류가 정해져야 시각이 필요한 경우)만 예외로 첫 질문만 냅니다.
  3. 질문에 선택지를 넣습니다. "취소가 무슨 뜻인가요"보다 세 선택지를 정의와 함께 제시하는 편이 고객이 답하기 쉽고, 답을 request_type 값으로 바로 옮길 수 있습니다.

보류 답변의 형식

보류는 실패가 아니라 정상 결과 중 하나입니다. rules.yaml 은 이것을 hold_policy 로 정해 두었습니다.

hold_policy:
  message: "다음 정보가 확인되지 않아 결론을 보류합니다: {missing}"
  evidence: [ops_manual:1]

보류 답변도 05-3의 네 부분 형식을 그대로 씁니다. 결론 자리에 보류 메시지가 들어가고, 미확인 사항이 비어 있지 않다는 점만 다릅니다. C007(Q19)의 보류 답변은 다음과 같습니다.

[결론] 다음 정보가 확인되지 않아 결론을 보류합니다: 사용량(문서 생성 수, 로그인 횟수)
[적용 조건] 프로 월간 구독, 결제 완료일 2025-09-02, 요청일 2025-09-08, 경과 6일.
  기간 요건(7일 이내)은 충족. 미사용 여부는 판정 불가.
[근거 조항] refund_policy_v2:3.1 (월간 7일 이내·미사용 시 전액 환불),
  refund_policy_v2:2.1 (미사용 정의), ops_manual:1 (확인 전 결론 보류)
[미확인 사항] 2025-09-02 주기의 문서 생성 수와 로그인 횟수.
  확인 후 미사용이면 19,900원 전액 환불, 사용이면 환불 불가·해지 안내.

미확인 사항에 "확인되면 어떻게 되는가"를 함께 적는 것이 요령입니다. 상담원은 사용량만 조회하면 결론까지 바로 갈 수 있고, 고객에게는 왜 기다려야 하는지 설명할 수 있습니다. questions.yaml 은 Q19에 "전액 환불합니다"를 금지 문구(forbidden_facts)로 두어, 보류해야 할 답변이 결론을 내면 오답으로 채점합니다.

여기까지가 예제 저장소에 구현된 범위입니다. 파이프라인은 확인되지 않은 항목을 찾아 추가 질문을 만들어 보류 답변에 담는 데까지 합니다. 반면 고객의 응답을 받아 상태에 합치고 같은 규칙을 다시 평가하는 대화 루프는 구현하지 않았습니다. 예제 파이프라인은 질문 하나에 한 번 답하는 형태이기 때문입니다. 이 되돌아가는 경로의 설계는 7-2에서 다루되, 실제 구현은 독자의 확장 과제로 남겨 둡니다. 전문 업무로 가면 requires 목록이 수십 개로 늘어나고 질문 순서를 정하는 일이 중요해지는데, 이는 10-3에서 세무 상담 사례로 확장합니다.

정리

  • 결론에 필요한 조건 목록은 규칙의 requires 이며, 운영 매뉴얼 1절의 확인 항목 표를 그대로 옮긴 것입니다. when 은 "조건이 참인가", requires 는 "판단할 사실이 있는가"를 묻습니다.
  • requires 항목은 known, unknown, not_applicable 로 구분하고, unknown 을 0이나 거짓으로 바꾸지 않습니다. 사용량 행이 없는 C007은 미사용이 아니라 미확인입니다. 이것이 열린 세계 가정을 규칙에 반영하는 방법입니다.
  • 추가 질문은 항목마다 미리 정한 문장을 쓰고, 결론을 바꿀 수 있는 항목만, 한 번에, 선택지를 넣어 묻습니다.
  • 보류 답변은 hold_policy 의 메시지를 결론 자리에 넣고, 미확인 사항에 "확인되면 어떻게 되는가"까지 적습니다. 구현은 7-2(되돌아가는 경로)와 7-4(형식)에서 이어집니다.
