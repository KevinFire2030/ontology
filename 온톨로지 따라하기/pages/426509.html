[검증] 적재 실행 검수 완료(2026-09-08, 별도 격리 DB에서 재실행 — 개념 22개 · 조항 108개 · 링크 56개 · 임베딩 생성) · PostgreSQL 16.2 + pgvector 0.6.2 실측 기준 (임베딩 단계는 OpenAI API 기준으로 서술)

이 절에서는 6장의 스키마를 실제로 만들고 데이터를 적재합니다. 정형 데이터 6종, 의미 모델(개념·관계·용어), 규정 판과 조항, 조항 링크, 그리고 임베딩까지 순서대로 넣고, 조회로 검증합니다. 실습을 마치면 질문 30개에 필요한 지식이 모두 데이터베이스 안에 들어 있게 됩니다.

실습 환경

  • PostgreSQL 16.2 + pgvector 0.6.2 (내장 경로, 03-1). Docker 경로도 같은 스크립트로 동작합니다.
  • Python 3.10, psycopg 3
  • 임베딩 단계만 OpenAI API 키가 필요합니다. 나머지는 키 없이 실행됩니다.
  • 스크립트는 테이블을 지우고 다시 만드므로 여러 번 실행해도 됩니다.

실습 1: 정형 데이터 적재

python ch06/load_structured.py

스크립트는 schema_structured.sql로 테이블 6개를 만들고 CSV를 COPY로 넣습니다.

# ch06/load_structured.py 발췌
with conn.cursor() as cur:
    with cur.copy(f"COPY {table} ({cols}) FROM STDIN") as cp:
        for r in rows:
            cp.write_row(r)

CSV의 빈 문자열은 None으로 바꿔 넣습니다. 그래야 suspended_at이나 promo_code 같은 컬럼이 빈 문자열이 아니라 NULL이 됩니다. 실측 출력입니다.

customers       14 rows
subscriptions   14 rows
payments        17 rows
usage_stats     13 rows
incidents        3 rows
team_members     9 rows

실습 2: 의미 모델·조항·링크 적재

python ch06/load_ontology.py

스크립트는 다섯 단계로 진행합니다. 개념(하위 유형 포함) → 관계 유형 → 용어 사전 → 규정 판과 조항 → 조항 링크 순서이며, 링크가 가리키는 조항과 개념이 실제로 있는지 검사한 뒤 한 트랜잭션으로 커밋합니다.

faq                  2025-03-01 ~ 현재         조항   4개
ops_manual           2025-07-01 ~ 현재         조항  15개
pricing_guide        2025-07-01 ~ 현재         조항   4개
refund_policy_v1     2024-01-01 ~ 2025-06-30   조항  22개
refund_policy_v2     2025-07-01 ~ 현재         조항  31개
terms_of_service     2024-01-01 ~ 현재         조항  32개
개념 22 / 관계 13 / 용어 10 / 조항 108 / 링크 56

마지막 줄의 개수는 적재가 끝난 뒤 각 테이블의 행 수를 count 집계로 센 실제 값입니다. 개념이 22개인 것은 model.yaml에 항목으로 적힌 개념 17개에, 이름만 하위 유형으로 등장하는 8개 중 이미 개념으로 정의되어 있지 않은 5개(IndividualCustomer, TeamCustomer, Outage, PlannedMaintenance, SeatChangeRequest)가 더해진 수입니다. 나머지 3개(RefundRequest, CancellationRequest, PaymentReversalRequest)는 개념 목록에도 있으므로 다시 삽입되지 않습니다. 하위 유형은 parent_id로 상위 개념을 가리킵니다.

[('CancellationRequest', 'CustomerRequest'), ('IndividualCustomer', 'Customer'),
 ('Outage', 'Incident'), ('PaymentReversalRequest', 'CustomerRequest'),
 ('PlannedMaintenance', 'Incident'), ('RefundRequest', 'CustomerRequest'),
 ('SeatChangeRequest', 'CustomerRequest'), ('TeamCustomer', 'Customer')]

실습 3: 임베딩 생성

python ch06/load_ontology.py --embed

--embed를 주면 적재 후 조항 108개를 임베딩해 embedding 컬럼에 저장합니다. 이 단계는 API 키가 필요하며, 완료되면 다음 줄이 출력됩니다. 토큰 수는 모델과 조항 길이에 따라 다릅니다.

임베딩 108개 저장 (토큰 ...)

임베딩은 구성 2 이후의 검색(common/retrieval.py)에서만 쓰입니다. 실습 4의 조회는 임베딩 없이 동작합니다.

SQL로 직접 확인해 볼 만한 조회 하나를 더 소개합니다. 2판 조항 중 1판 조항을 대체한 것과 새로 생긴 것을 나누는 조회입니다.

SELECT c.clause_id, c.heading,
       CASE WHEN l.to_ref IS NULL THEN '신설' ELSE '대체: ' || l.to_ref END AS origin
FROM clauses c
LEFT JOIN clause_links l ON l.from_clause = c.clause_id AND l.rel = 'supersedes'
WHERE c.doc_id = 'refund_policy_v2' AND c.clause_no LIKE '%.%'
ORDER BY c.clause_no;

실측 결과 1조(적용 범위), 2조(용어의 정의), 4조 3항(위약금 없음), 5조 3항(최소 좌석), 6조(학생 요금제)가 신설로 나오고 나머지 13개 항은 1판 조항을 대체한 것으로 나옵니다. 규정 개정 내역을 링크 데이터만으로 재구성할 수 있다는 뜻입니다.

관찰 포인트

  • 적재 스크립트가 모델의 빈틈을 찾습니다. 첫 적재에서 링크 검사가 "concept:Unused가 없다"고 경고했고, 그 덕에 파생 개념 하나를 모델에 추가했습니다(06-3). 적재를 검증 단계로 쓰면 모델 파일과 데이터베이스가 어긋나는 일이 줄어듭니다.
  • None과 False는 다릅니다. C007의 unused가 None인 것이 7장에서 보류 판단을 만드는 유일한 근거입니다. 적재나 조회 어디에서든 NULL을 기본값으로 바꾸면 그 순간 "미확인"이 "미사용" 또는 "사용"이 됩니다.
  • 조 단위와 항 단위가 둘 다 필요합니다. 준용은 조 단위(6.1 → 3, 4), 인용은 항 단위(ops_manual:2 → terms_of_service:9.3)로 걸립니다. 한 단위만 넣으면 링크의 절반을 표현할 수 없습니다.
  • 임베딩은 마지막이고 선택입니다. 조항·링크·개념 테이블은 임베딩 없이 완전하며, 판단 기능은 임베딩에 의존하지 않습니다.

더 해 보기

  • 요금 안내의 가격표를 plan_prices 함수 대신 유효기간을 가진 테이블로 옮겨 보세요. 06-2의 패턴이 그대로 적용됩니다.
  • clause_links에 관계 종류를 하나 추가해 보세요. 예를 들어 "관련 있음(related_to)"으로 FAQ 항목과 운영 매뉴얼 절을 연결합니다. 이때 YAML에 관계만 적어서는 적재되지 않습니다. clause_links.rel의 CHECK 제약이 supersedes, applies_mutatis_mutandis, cites, defines 네 값만 허용하기 때문에, 스키마의 CHECK에 related_to를 먼저 넣고 테이블을 다시 만들어야 합니다. 그 다음 06-4의 조회 함수(impact_of 등)가 새 관계를 어떻게 다룰지 정해 코드를 고치고 나서야 결과가 어떻게 달라지는지 확인할 수 있습니다. 제약 확장 → 적재 → 조회 API 수정까지가 한 묶음입니다.
  • 06-2의 유효기간 겹침 검사를 load_ontology.py의 마지막 단계에 넣어 보세요.

정리

  • 정형 데이터 6종, 개념 22, 관계 13, 용어 10, 조항 108, 링크 56이 적재되었고 조회 함수로 질문 세트와의 대응을 확인했습니다.
  • 임베딩은 별도 옵션이며 판단 기능은 임베딩 없이 동작합니다.
  • 다음 장에서 이 데이터를 검색·SQL·규칙과 엮어 답변을 만드는 파이프라인을 구현합니다.
