4장에서 만든 최소 의미 모델(model.yaml)은 "환불 요청이란 무엇인가", "결제와 규정 판은 어떤 관계인가"를 정의했습니다. 그런데 실제 상담에서 필요한 것은 "그래서 이 고객에게 환불이 되는가"입니다. 이 질문에 답하려면 원칙과 예외가 얽힌 구조를 풀어서 기계가 따라갈 수 있는 형태로 적어야 합니다. 이 절에서는 노트클라우드 환불 규정 제2판을 재료로 그 구조를 분석하고, 예외를 어디에 둘지 판단하고, 충돌을 해결하는 우선순위를 정합니다.

환불 규정 제2판의 원칙과 예외 구조

환불 규정 제2판(data/docs/refund_policy_v2.md)을 조항 단위로 읽으면 크게 두 종류의 문장이 보입니다. 하나는 "이런 경우 이렇게 한다"는 원칙이고, 다른 하나는 "단, 이런 경우에는 그렇지 않다"는 예외입니다. 아래 표는 그 구조를 정리한 것입니다.

구분 조항 내용 결과
원칙 3조 1항 월간 구독, 결제 완료일로부터 7일 이내, 미사용 전액 환불
원칙 3조 2항 월간 구독, 7일 경과 또는 사용 환불 불가, 해지 안내
원칙 4조 1항 연간 구독, 30일 이내 전액 환불
원칙 4조 2항·4항 연간 구독, 30일 경과 잔여 기간 일할 환불, 연간 할인분 사용 비례 환수
원칙 5조 1항 팀 좌석 축소 다음 주기 반영, 차액 환불 없음
예외 5조 3항 팀 좌석을 3좌석 미만으로 축소 불가, 프로 요금제 전환 필요
준용 6조 1항 학생 요금제 베이직 규정을 그대로 적용
예외 6조 2항 학생 인증 만료 후 베이직 가격으로 자동 갱신, 7일 이내 사용 여부와 관계없이 전액 환불
예외 7조 1항 프로모션 코드 적용 결제 전액 환불 기간 안에서만 환불
예외 7조 2항 약관 위반 계정 정지 잔여 기간 환불 불가

여기서 눈여겨볼 점이 세 가지 있습니다.

첫째, 예외는 원칙보다 강합니다. 3조 2항은 "사용했으면 환불 불가"라고 하지만, 6조 2항은 "사용 여부와 관계없이 전액 환불"이라고 합니다. C009처럼 문서 3건을 만들고 10번 로그인한 학생 고객이라도 인증 만료 후 갱신된 결제라면 9,900원을 전액 돌려받습니다(Q21). 두 조항이 동시에 참일 때 6조 2항이 이겨야 합니다.

둘째, 예외에도 방향이 다릅니다. 6조 2항은 고객에게 유리한 쪽으로 원칙을 넓히고, 7조 1항·2항은 불리한 쪽으로 원칙을 좁힙니다. 7조 2항은 어떤 조건이 충족되어도 환불을 막는 "문 앞의 검문"이고, 6조 2항은 원칙에서 탈락한 고객을 다시 건져 올리는 "구제 조항"입니다.

셋째, 예외가 다른 조항을 참조합니다. 7조 1항의 "전액 환불 기간"은 3조 1항과 4조 1항이 정의한 기간을 가리킵니다. 프로모션 결제 자체를 판단하는 규칙이 아니라, 다른 규칙의 결과 범위를 좁히는 규칙입니다. 이런 참조 관계는 05-3에서 근거 연결로 다시 다룹니다.

예외를 개념으로 둘지 규칙으로 둘지

예외를 발견하면 설계자는 두 갈래 앞에 섭니다. 온톨로지에 하위 개념으로 넣을 것인가, 아니면 규칙 파일에 조건으로 넣을 것인가입니다. 예를 들어 "프로모션 결제"를 Payment 의 하위 유형 PromoPayment 로 만들 수도 있고, Payment 에 promo_code 속성만 두고 규칙에서 promo_code 가 있는지 검사할 수도 있습니다.

이 책에서 쓰는 판단 기준은 다음과 같습니다.

판단 기준 개념(하위 유형)으로 둔다 규칙(overrides)으로 둔다
그 구분이 여러 질문·여러 조항에서 반복해서 쓰이는가 반복된다 한두 조항에서만 쓰인다
그 구분이 없으면 다른 정의가 불완전해지는가 그렇다 아니다
사람이 대화에서 그것을 명사로 부르는가 "결제 취소", "정기 점검"처럼 명사로 부른다 "프로모션 코드가 있으면"처럼 조건으로 말한다
결론이 규정 판에 따라 바뀌는가 바뀌지 않는다 바뀐다(1판 불가, 2판 기간 내 가능)

이 기준으로 노트클라우드의 예외를 나누면 다음과 같습니다.

  • 개념으로 둔 것: CustomerRequest 의 하위 유형 네 가지(환불·해지·결제 취소·좌석 변경), Incident 의 하위 유형 Outage 와 PlannedMaintenance. 이 구분은 질문 30개 중 십여 개에 걸쳐 쓰이고, "해지는 금액 반환이 없다"처럼 정의 자체가 다릅니다.
  • 규칙으로 둔 것: 프로모션 결제(7조 1항), 계정 정지(7조 2항), 학생 인증 만료 갱신(6조 2항), 최소 좌석(5조 3항). 이들은 각각 한 조항에서만 쓰이고, 프로모션은 규정 판에 따라 결론이 뒤집힙니다. 모델에서는 promo_code, account_status, student_verified_until, seats 같은 속성으로만 남기고 판단은 rules.yaml 에 맡깁니다.

하위 유형을 늘리면 개념 수가 조건 조합만큼 폭발하고, 규정이 바뀔 때마다 개념 정의를 고쳐야 합니다. 05-5에서 다시 강조하겠지만, 온톨로지는 "무엇이 무엇인가"를 맡고 규칙은 "언제 어떤 결론이 나는가"를 맡습니다.

규칙 파일의 기본 형태

rules.yaml 의 규칙 하나는 다음 다섯 요소로 이루어집니다.

- id: monthly_full_refund
  when: [request_type == Refund, billing_cycle == monthly,
         days_since_payment <= 7, unused == true]
  requires: [paid_at, docs_created, logins]
  result: "전액 환불"
  evidence: [refund_policy_v2:3.1, refund_policy_v2:2.1]

when 은 모두 참이면 규칙이 적용되는 조건, requires 는 결론을 내리기 전에 반드시 확인되어야 하는 사실(하나라도 모르면 보류, 05-4), result 는 결론, evidence 는 근거 조항(05-3)입니다. 여기에 예외와 우선순위를 위한 overrides 와 priority 가 붙습니다. when 과 requires 를 나눈 이유가 중요합니다. when 은 "조건이 참인가"를 묻고, requires 는 "조건을 판단할 재료가 있는가"를 묻습니다. unused 가 거짓이면 환불 불가라는 결론이 나오지만, 사용량 기록이 없으면 결론 자체를 내지 않습니다.

우선순위와 충돌 해결

한 요청에 여러 규칙이 동시에 맞을 수 있습니다. C012는 프로 연간 구독을 2025년 3월에 결제했으니 4조 2항의 일할 환불 조건에 맞지만, 8월 1일 계정이 정지되어 7조 2항에도 맞습니다. 두 규칙이 서로 다른 결론을 내면 어느 쪽을 택할지 정해 두어야 합니다. rules.yaml 은 두 가지 장치를 씁니다.

첫째는 priority 입니다. 숫자가 클수록 먼저 평가하고, 결론이 나오면 뒤의 규칙은 보지 않습니다.

규칙 id priority 역할 근거
exclude_suspended 100 계정 정지면 환불 불가 2판 7조 2항, 1판 5조 2항
exclude_non_admin_team 100 팀 구성원 요청은 처리 불가 약관 8조 1항·2항
promo_v1_no_refund 90 1판 대상 프로모션 결제는 환불 불가 1판 5조 1항
promo_v2_window_only 90 2판 대상 프로모션 결제는 전액 환불 기간 안에서만 2판 7조 1항
monthly_full_refund 등 원칙 규칙 미기재(기본값 0) 월간·연간 원칙 3조·4조

계정 정지와 요청자 권한을 100으로 둔 것은 "판단할 자격이 있는가"를 묻는 검문이기 때문입니다. 프로모션을 90으로 둔 것은 검문을 통과한 뒤 환불 범위를 좁히는 조건이기 때문입니다. 원칙 규칙은 마지막에 평가됩니다.

둘째는 overrides 입니다. priority 가 "먼저 본다"는 전역 순서라면, overrides 는 "이 규칙이 맞으면 저 규칙은 무시한다"는 두 규칙 사이의 관계입니다.

이기는 규칙 지는 규칙 뜻
student_expired_renewal monthly_no_refund 인증 만료 후 갱신 결제는 사용했어도 7일 이내면 전액 환불
seat_minimum seat_decrease 3좌석 미만 축소는 "다음 주기 반영"이 아니라 "불가"
maintenance_not_incident incident_credit 정기 점검은 24시간이 넘어도 장애 보상 대상이 아님

overrides 를 쓰는 규칙에는 priority 를 따로 붙이지 않았습니다. 관계가 두 규칙 사이에만 성립하기 때문입니다. 규칙이 수십 개로 늘어나면 priority 숫자만으로 관계를 읽기 어려워지므로, 가능하면 overrides 로 관계를 명시하고 priority 는 검문 규칙처럼 명백히 앞서야 하는 소수에만 쓰는 것을 권합니다.

충돌 해결 순서를 그림으로 그리면 다음과 같습니다.

요청 접수
  │
  ├─ priority 100: 계정 정지? 팀 구성원 요청?  ── 맞으면 여기서 종료
  │
  ├─ priority 90: 프로모션 결제?             ── 맞으면 환불 범위를 제한
  │
  └─ 원칙 규칙(월간·연간·좌석·장애)
        └─ overrides 로 지정된 예외가 맞으면 원칙 결론을 대체

표현 방식 비교표

같은 원칙·예외 구조를 어디에 적을지는 네 가지 선택지가 있습니다. 이 책은 규칙 파일을 택했지만, 다른 방식이 맞는 상황도 있습니다.

방식 모습 장점 단점 맞는 상황
조건문 코드 if 문이 중첩된 함수 실행이 빠르고 테스트하기 쉬움 규정 담당자가 읽을 수 없고, 근거 조항이 코드 주석에 묻힘 규칙이 5개 이내이고 거의 바뀌지 않을 때
결정표 조건 열과 결과 열로 된 표 빠진 조합이 눈에 보이고, 비개발자도 검토 가능 조건이 늘면 열이 폭발하고, 시점·근거를 넣기 어려움 조건이 3~4개이고 조합이 유한할 때
규칙 파일(이 책) when·requires·result·evidence·overrides 근거·보류·우선순위를 함께 기록, 규정 변경 시 해당 규칙만 수정 평가기를 직접 만들어야 하고, 규칙 사이 상호작용을 검증해야 함 규칙이 수십 개이고 규정이 정기적으로 바뀔 때
LLM 프롬프트 서술 규정 원문을 컨텍스트에 넣고 판단을 맡김 구현이 가장 빠르고 새 규정을 바로 반영 같은 입력에 다른 결론, 예외 누락, 근거 조항 오인용(1장의 오답 유형) 규칙이 아직 정리되지 않은 탐색 단계

1장의 기본 RAG는 네 번째 방식이었고, 6조 2항 같은 구제 조항을 놓치거나 1판의 "프로모션 환불 불가"를 현재 규정으로 잘못 적용했습니다(Q10·Q21). 규칙 파일은 그 판단을 코드가 하게 하고 LLM에는 결과와 근거만 넘깁니다. 7장에서 이 규칙을 평가하는 코드(ch07/rules.py)를 만듭니다.

정리

  • 규정을 조항 단위로 읽어 원칙과 예외를 표로 나눕니다. 예외는 원칙보다 강하고, 유리한 방향(구제)과 불리한 방향(제외)이 있으며, 다른 조항을 참조하기도 합니다.
  • 예외를 개념으로 둘지 규칙으로 둘지는 반복 사용 여부, 정의의 독립성, 명사로 불리는지, 규정 판에 따라 바뀌는지로 판단합니다. 노트클라우드에서는 요청 종류와 장애 종류만 개념으로 두고 나머지 예외는 규칙으로 두었습니다.
  • 규칙은 when·requires·result·evidence 를 기본으로 하고, 충돌은 priority(검문 규칙 100, 범위 제한 90)와 overrides(두 규칙 사이 관계)로 해결합니다.
  • 조건문 코드, 결정표, 규칙 파일, LLM 프롬프트 서술은 각각 맞는 상황이 다릅니다. 이 책은 근거와 보류를 함께 기록할 수 있는 규칙 파일을 택했습니다.
