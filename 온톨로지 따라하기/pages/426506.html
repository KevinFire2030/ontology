5-2에서 설계한 시점 규칙을 테이블로 옮깁니다. 핵심은 "규정 판은 유효기간을 갖고, 결제는 결제 완료일로 판을 고른다"는 것입니다. 이 절에서는 유효기간 컬럼, 특정 시점의 판을 고르는 SQL, 이력 테이블과의 관계, 그리고 겹치는 유효기간이라는 함정을 다룹니다.

규정 판 테이블

CREATE TABLE policy_versions (
    doc_id     text PRIMARY KEY,
    title      text NOT NULL,
    valid_from date NOT NULL,
    valid_to   date,                               -- NULL = 종료일 미정 (현재 유효 여부는 기준일 조건으로 판단)
    CHECK (valid_to IS NULL OR valid_to >= valid_from)
);

행은 문서 프런트매터에서 그대로 옵니다. 적재 결과입니다.

faq                  2025-03-01 ~ 현재         조항   4개
ops_manual           2025-07-01 ~ 현재         조항  15개
pricing_guide        2025-07-01 ~ 현재         조항   4개
refund_policy_v1     2024-01-01 ~ 2025-06-30   조항  22개
refund_policy_v2     2025-07-01 ~ 현재         조항  31개
terms_of_service     2024-01-01 ~ 현재         조항  32개

valid_to가 NULL이면 종료일이 아직 정해지지 않은 판이라는 뜻입니다. 종료일 미정과 "지금 유효함"은 같은 말이 아닙니다. 시행 전인 새 판도 종료일은 비어 있기 때문입니다. 기준일 d 시점에 유효한 판을 고르려면 valid_from <= d 와 (valid_to IS NULL OR valid_to >= d) 를 함께 걸어야 합니다. 종료일 자리에 특정 날짜를 미리 적지 않는 이유는 그 날짜가 언제일지 아무도 모르기 때문입니다. 새 판이 시행되는 날 이전 판의 valid_to를 채우는 것이 유일한 갱신입니다.

특정 시점의 판 고르기

결제 완료일이 주어졌을 때 적용 판을 고르는 조회입니다. 06-4의 조회 함수 policy_version_for가 이 SQL을 실행합니다.

SELECT doc_id FROM policy_versions
WHERE doc_id LIKE 'refund_policy%'
  AND valid_from <= :paid_at
  AND (valid_to IS NULL OR valid_to >= :paid_at)
ORDER BY valid_from DESC LIMIT 1;

실측 결과입니다.

적용 판(2025-06-20 결제): refund_policy_v1
적용 판(2025-08-20 결제): refund_policy_v2

여기까지가 "기본 판"입니다. 약관 9조 3항의 유리한 규정 적용은 판 하나를 고르는 문제가 아니라 두 판으로 각각 계산해 비교하는 문제이므로, SQL이 아니라 07-2의 규칙 코드에서 처리합니다. 데이터베이스는 "어떤 판이 언제 유효했는가"라는 사실만 답하고, "그중 무엇을 적용할 것인가"라는 판단은 규칙 층에 둡니다. 5-5의 경계입니다.

결제 주기와 시점

시점은 규정에만 있는 것이 아닙니다. 구독에는 현재 결제 주기가 있고, 사용량은 결제 주기마다 기록되고, 장애는 시작·종료 시각이 있습니다. 이들을 연결하는 조건은 모두 날짜 비교입니다.

관계 조건 어디에서 쓰는가
결제 → 규정 판 paid_at이 valid_from과 valid_to 사이 적용 판 결정 (governed_by)
구독 → 현재 결제 payments.paid_at = subscriptions.current_period_start 환불 대상 금액
구독 → 현재 사용량 usage_stats.period_start = current_period_start 미사용 판정
구독 → 장애 장애 기간이 결제 주기와 겹침 크레딧 대상 (affected_by)

model.yaml에서 governed_by와 affected_by를 "파생 관계(derived)"로 표시한 이유가 여기 있습니다. 이 관계들은 테이블에 저장하지 않고 날짜 비교로 계산합니다. 저장하면 결제일이나 유효기간이 바뀔 때마다 갱신해야 하는 중복이 생깁니다.

자동 갱신 결제에서 주의할 점이 있습니다. 약관 3조 3항은 갱신 결제를 새 결제 완료일 기준으로 봅니다. 그래서 subscriptions에는 처음 결제일(first_paid_at)과 현재 주기 시작일(current_period_start)이 따로 있고, 규정 판을 고를 때는 현재 주기의 결제일을 씁니다. C002는 2025년 3월에 처음 구독했지만 9월 3일 갱신 결제가 기준이므로 2판 대상입니다.

이력 테이블

이 책의 예제는 규정 판을 문서 단위로 두었습니다. 1판과 2판이 별개 문서이고, 조항 사이의 대체 관계(supersedes)를 clause_links에 기록합니다. 규모가 작을 때는 이것으로 충분합니다.

조항 단위로 자주 개정되는 규정이라면 조항 자체에 유효기간을 두는 편이 낫습니다.

-- 조항 단위 이력 (이 책의 예제에는 없음 — 설계 예시)
CREATE TABLE clause_history (
    clause_key  text NOT NULL,       -- '환불규정:4.1' 처럼 판을 넘어 같은 조항을 가리키는 키
    valid_from  date NOT NULL,
    valid_to    date,
    content     text NOT NULL,
    PRIMARY KEY (clause_key, valid_from)
);

두 방식의 차이는 "무엇이 바뀌었는가"를 어디에 기록하느냐입니다.

방식 단위 장점 단점
문서 판 + 대체 링크 (이 책) 문서 원문을 그대로 보관, 인용이 쉬움 바뀌지 않은 조항도 새 판에 다시 들어감
조항 이력 조항 바뀐 조항만 새 행, 특정 시점 조문 조회가 SQL 한 줄 문서 전체를 재구성해야 하고 조항 키 관리가 필요

세무 법령처럼 조문 단위로 개정되고 개정 이력 자체가 근거가 되는 영역에서는 조항 이력 방식이 맞습니다. 10장에서 이 점을 다시 봅니다.

함정: 겹치는 유효기간

같은 문서 계열의 판 두 개가 같은 날짜에 유효하면 위 SQL은 valid_from이 늦은 것을 고르지만, 그것이 의도인지는 알 수 없습니다. 대개는 데이터 오류입니다. 적재할 때 겹침을 검사하는 조회를 두는 것이 안전합니다.

SELECT a.doc_id, b.doc_id
FROM policy_versions a JOIN policy_versions b
  ON a.doc_id < b.doc_id
 AND split_part(a.doc_id, '_v', 1) = split_part(b.doc_id, '_v', 1)
 AND a.valid_from <= COALESCE(b.valid_to, 'infinity')
 AND b.valid_from <= COALESCE(a.valid_to, 'infinity');

이 조회가 행을 돌려주면 유효기간이 겹치는 것입니다. 노트클라우드 데이터에서는 0행이 나와야 하고, 실측에서도 0행이었습니다. 다만 이 점검은 사람이 따로 돌리는 조회입니다. 예제의 적재 스크립트(ch06/load_ontology.py)는 겹침을 자동으로 막지 않고, policy_versions 테이블의 CHECK 제약도 한 행 안에서 valid_to가 valid_from보다 앞서지 않는지만 확인합니다. 판과 판 사이의 겹침은 검사 범위 밖입니다.

PostgreSQL에는 이런 검사를 선언으로 대신하는 방법이 있습니다. daterange 타입과 EXCLUDE 제약을 쓰면 겹치는 기간의 삽입 자체가 거부됩니다. btree_gist 확장이 필요한데, 집필 환경의 내장 PostgreSQL에는 이 확장이 없어 본문 실습은 코드 검사로 대신했습니다. Docker 경로(pgvector/pgvector:pg16, btree_gist 1.7)에서는 다음이 그대로 동작합니다.

-- Docker 경로 (btree_gist 확장 필요)
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE policy_versions ADD COLUMN family text GENERATED ALWAYS AS (split_part(doc_id, '_v', 1)) STORED;
ALTER TABLE policy_versions ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (family WITH =, daterange(valid_from, COALESCE(valid_to, 'infinity'), '[]') WITH &&);

실제로 걸어 두고 refund_policy_v2(2025-07-01~현재)와 겹치는 판을 넣어 보면 이렇게 거부됩니다.

ERROR:  conflicting key value violates exclusion constraint "no_overlap"

정리

  • 규정 판은 valid_from·valid_to를 가지며, 결제 완료일로 판을 고르는 것은 SQL 한 줄입니다.
  • 유리한 규정 적용은 판 선택이 아니라 비교 판단이므로 규칙 층(07-2)에 둡니다.
  • 결제·사용량·장애와의 시점 관계는 저장하지 않고 날짜 비교로 계산합니다.
  • 조항 단위 개정이 잦은 영역은 조항 이력 테이블이 맞고, 판 사이의 유효기간 겹침은 위의 별도 SQL로 점검합니다. 예제 로더에는 자동 검사가 없고, 스키마의 CHECK는 한 행 안에서 시작일과 종료일의 순서만 봅니다.
  • 다음 절에서 조항 본문과 임베딩을 의미 모델에 연결합니다.
