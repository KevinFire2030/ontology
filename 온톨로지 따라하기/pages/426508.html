테이블이 준비되었으니 이제 파이프라인이 쓸 조회 함수를 만듭니다. 이 함수들이 "의미 모델의 API"입니다. 7장의 파이프라인이 직접 호출하고, LLM에게 도구로 노출할 수도 있습니다. 이 절에서는 함수의 설계 원칙, 세 묶음의 함수, 그리고 실측 결과를 봅니다.

설계 원칙

함수를 설계할 때 지킨 원칙은 세 가지입니다.

  • 질문에 답하는 단위로 만든다. "테이블을 읽는다"가 아니라 "이 결제에 적용되는 판은 무엇인가", "이 조항이 바뀌면 무엇을 점검해야 하는가"처럼 업무 질문 하나에 함수 하나입니다.
  • 사실만 돌려주고 판단하지 않는다. policy_version_for는 결제일에 유효한 판을 돌려줄 뿐, 유리한 규정을 고르지 않습니다. 판단은 07-2의 규칙 층이 합니다.
  • 모르는 것은 모른다고 돌려준다. 사용량 기록이 없으면 None을 돌려주고, 호출한 쪽이 "미확인"으로 다룹니다. 기본값으로 0을 채우지 않습니다.

규정 판·조항 함수

함수 입력 돌려주는 것 쓰이는 곳
policy_version_for 결제 완료일 그 날짜에 유효한 환불 규정 판 ID 07-2 판 선택
clause 조항 ID 조항 본문 근거 표시
clauses_of 문서 ID, 조 번호 그 조의 항 목록 준용 조 전체 가져오기
linked 조항 ID, 관계, 방향 연결된 조항·개념 ID 목록 준용·대체·인용 탐색
resolve_mutatis_mutandis 조항 ID 준용 대상 조항 Q09, Q20
superseded_by 1판 조항 ID 대체한 2판 조항 판 비교 설명
impact_of 조항 ID 인용하는 항목, 정의하는 개념, 준용하는 조항 Q30, 11-2

linked 함수 하나가 여러 함수의 바탕입니다. 방향을 뒤집는 reverse 인자가 있어 "이 조항이 가리키는 것"과 "이 조항을 가리키는 것"을 같은 방식으로 찾습니다.

# ch06/api.py 발췌
def linked(clause_id: str, rel: str, reverse: bool = False) -> list[str]:
    with db.connect() as c:
        if reverse:
            rows = c.execute("SELECT from_clause FROM clause_links WHERE rel=%s AND to_ref=%s ORDER BY 1",
                             (rel, clause_id)).fetchall()
        else:
            rows = c.execute("SELECT to_ref FROM clause_links WHERE rel=%s AND from_clause=%s ORDER BY 1",
                             (rel, clause_id)).fetchall()
    return [r[0] for r in rows]

적용 판(2025-08-20 결제): refund_policy_v2
준용(refund_policy_v2:6.1): ['refund_policy_v2:3', 'refund_policy_v2:4']

마지막 줄이 Q30의 답입니다. 2판 4조 1항이 바뀌면 FAQ의 "결제와 구독" 절과 운영 매뉴얼 2절을 함께 점검해야 합니다. 이 답은 문서 검색으로는 나오지 않습니다. 질문에 "FAQ"나 "운영 매뉴얼"이라는 단어가 없기 때문입니다. 링크가 있어야 나옵니다.

개념·용어 함수

함수 입력 돌려주는 것
concept 개념 ID 정의, 상위 개념, 속성, 정의 조항
normalize_term 고객·문서의 표현 해당할 수 있는 표준 용어 목록 
개념(Unused): {'concept_id': 'Unused', 'label': '미사용',
  'definition': '한 결제 주기 동안 새로 생성한 문서가 0건이고 로그인이 3회 이하인 상태 (제2판 2조 1항). ...',
  'defined_in': ['refund_policy_v2:2.1']}
용어('취소해 주세요'): [('CancellationRequest', '취소해 주세요'), ('PaymentReversalRequest', '취소')]

normalize_term이 후보를 하나가 아니라 목록으로 돌려주는 점이 중요합니다. "취소해 주세요"는 해지일 수도 결제 취소일 수도 있습니다. 함수가 임의로 하나를 고르면 4-2에서 정리한 용어 혼동이 코드 안에서 다시 일어납니다. 후보가 둘 이상이면 07-1의 질문 분석이 확인 요청을 냅니다.

정형 데이터 함수

함수 입력 돌려주는 것
customer_context 고객 ID 고객·구독·현재 주기 결제·사용량·팀 관리자를 한 번에
plan_prices 요금제, 날짜 그 날짜의 월간·연간 정가
incident 장애 ID 또는 날짜 장애 정보
incidents_overlapping 기간 그 기간과 겹치는 장애
subscriptions_paid_before 날짜 그 날짜 이전에 결제되어 유효한 구독

customer_context는 조인 하나로 판단에 필요한 사실을 모읍니다. 사용량은 LEFT JOIN이라 기록이 없으면 NULL이 됩니다.

# ch06/api.py 발췌
d["usage_known"] = d["docs_created"] is not None
d["unused"] = (d["docs_created"] == 0 and d["logins"] <= 3) if d["usage_known"] else None

usage_known과 unused를 따로 두는 것이 "모르는 것은 모른다고 돌려준다" 원칙의 구현입니다. C007의 실측 결과입니다.

C007: {..., 'paid_at': datetime.date(2025, 9, 2), 'amount': 19900,
       'docs_created': None, 'logins': None, 'usage_known': False, 'unused': None}

unused가 False가 아니라 None입니다. False였다면 "사용했다"는 뜻이 되어 환불 불가로 흘러가고, 기본값 True였다면 전액 환불로 흘러갑니다. None이어야 07-2에서 보류가 됩니다.

plan_prices는 요금 안내 문서의 가격표를 코드에 둔 것입니다. 2025년 7월 1일 개정 전후 가격을 날짜로 구분합니다. 규모가 커지면 가격표도 유효기간을 가진 테이블로 옮기는 것이 맞습니다. 여기서는 06-2의 시점 패턴이 가격에도 똑같이 적용된다는 점만 보여 줍니다.

subscriptions_paid_before는 Q29(규정 개정 시 재점검 대상)의 후보를 돌려줍니다.

개정 전 결제 유효 구독: [('C004', 'yearly', None, 'active'), ('C010', 'yearly', 'SPRING20', 'active'), ('C012', 'yearly', None, 'suspended')]

세 건이 후보이고, 이 중 실제 대상이 누구인지는 규칙(프로모션 기간 경과, 계정 정지)이 걸러냅니다. 함수는 후보를 주고 규칙이 판단합니다.

LLM 도구로 노출하기

이 함수들은 그대로 LLM의 도구(function calling)로 등록할 수 있습니다. 이름과 입력이 이미 업무 질문 단위이기 때문입니다. 다만 이 책의 파이프라인은 도구 호출 방식을 쓰지 않고, 파이프라인 코드가 질문 분석 결과에 따라 함수를 직접 호출한 뒤 결과를 LLM에 넘깁니다. 두 방식의 비교는 07-3에서 다룹니다. 어느 쪽이든 함수 자체는 같습니다.

함수 시그니처 설명 (도구 등록 시 description)
policy_version_for(paid_at) 결제 완료일에 적용되는 환불 규정 판을 돌려줍니다
customer_context(customer_id) 고객의 구독·현재 결제·사용량·계정 상태를 돌려줍니다. 사용량이 없으면 usage_known이 false입니다
resolve_mutatis_mutandis(clause_id) 조항이 준용하는 조항들을 돌려줍니다
impact_of(clause_id) 조항이 바뀌면 함께 점검할 문서 항목과 개념을 돌려줍니다
normalize_term(text) 표현에 해당할 수 있는 표준 용어 후보를 돌려줍니다. 둘 이상이면 확인이 필요합니다

정리

  • 조회 함수는 업무 질문 단위로 만들고, 사실만 돌려주며, 모르는 것은 None으로 돌려줍니다.
  • 규정 판·조항 함수, 개념·용어 함수, 정형 데이터 함수 세 묶음이 있고 모두 SQL 한두 개입니다.
  • 준용·대체·인용 탐색은 linked 함수 하나에 방향 인자를 준 것이며, 영향 범위 조회가 Q30의 답을 냅니다.
  • 다음 절에서 스키마를 만들고 데이터를 적재하는 실습을 처음부터 끝까지 진행합니다.
