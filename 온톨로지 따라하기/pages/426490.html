[검증] ontology-tutorial 저장소 구조 기준 (PostgreSQL 16.2 + pgvector 0.6.2 실측)

예제 저장소 https://github.com/ady95/ontology-tutorial 는 장별 폴더와 공통 모듈, 그리고 책 전체가 공유하는 데이터 폴더로 이루어져 있습니다. 이 절에서는 폴더 구조, 장과 코드의 대응, 공통 모듈의 역할, 실행 순서를 정리합니다. 이후 장에서 코드를 발췌할 때는 항상 이 저장소의 파일 경로를 함께 적습니다.

폴더 구조

ontology-tutorial/
├── common/              공통 모듈
│   ├── db.py            PostgreSQL 연결 (Docker / 내장 자동 구분)
│   ├── llm.py           채팅·임베딩 호출, 토큰·시간 누적
│   └── evaluate.py      질문 30개 채점기, 구성 비교표
├── data/
│   ├── docs/            규정 문서 6종 (마크다운 + 프런트매터)
│   ├── structured/      고객·구독·결제·사용량·장애·팀원 CSV
│   ├── eval/            questions.yaml — 질문 30개와 정답
│   ├── ontology/        model.yaml, glossary.yaml, rules.yaml
│   └── tax/             10장 세무 사례 문서·정형 데이터·질문 10개

data 폴더가 특정 장에 속하지 않고 루트에 있는 것이 이 저장소의 특징입니다. 같은 문서, 같은 데이터, 같은 질문을 모든 구성이 공유해야 비교가 성립하기 때문입니다.

장과 코드의 대응

장 폴더·파일 만드는 것
01 ch01/rag_basic.py 구성 1(기본 RAG)과 첫 채점 결과
03 common/, ch03/check_env.py 연결 확인, 채점기
04 data/ontology/model.yaml, glossary.yaml, ch04/validate_model.py 최소 의미 모델과 용어 사전
05 data/ontology/rules.yaml 조건·예외·시점·근거를 담은 판단 규칙
06 ch06/ 정형 테이블, 의미 모델 테이블, 조항·임베딩 테이블, 조회 함수
07 ch07/ 질문 분석 → 검색·SQL·규칙 → 근거 있는 답변 파이프라인
08 ch08/ 구성 2·3 구현과 다섯 구성 비교 실행
09 ch09/ 재귀 CTE 그래프 탐색, AGE(Docker), 구성 5
10 ch10/, data/tax/ 세무 상담 사례로 확장한 데이터·규칙과 세 구성 비교
11 ch11/ 의미 모델을 OKF 번들로 내보내고 다시 읽기

4장과 5장은 코드보다 YAML 파일이 산출물입니다. 의미 모델을 코드가 아니라 데이터로 두는 이유는 6장에서 테이블로, 7장에서 LLM 컨텍스트로, 9장에서 그래프로 같은 파일을 여러 번 쓰기 때문입니다.

공통 모듈 세 개

db.py는 접속 문자열을 정하고 vector 확장을 활성화한 연결을 돌려줍니다. DATABASE_URL이 있으면 그 서버로, 없으면 내장 PostgreSQL로 갑니다(03-1). 모든 장의 코드는 다음 한 줄로 데이터베이스를 씁니다.

from common import db
with db.connect() as conn:
    rows = conn.execute("select ...").fetchall()

connect()는 autocommit이 기본입니다. 실습 코드가 짧은 문장을 여러 개 실행하는 형태라 트랜잭션을 명시적으로 관리할 일이 드물기 때문입니다. 적재 스크립트처럼 원자성이 필요한 곳은 autocommit=False로 열고 직접 커밋합니다.

llm.py는 03-2에서 본 대로 chat(), chat_json(), embed() 세 함수와 usage 누적기를 제공합니다.

evaluate.py는 03-4에서 자세히 봅니다. 파이프라인 함수를 받아 질문 30개를 넣고 채점해 results 폴더에 저장합니다.

실행 순서

처음 시작할 때의 순서입니다.

python ch03/check_env.py            # 1. 환경 확인
python ch06/load_structured.py      # 2. 정형 데이터 적재
python ch01/rag_basic.py --index    # 3. 구성 1 인덱스 생성 (임베딩 1회)
python ch01/rag_basic.py --eval     # 4. 구성 1 채점 → results/config1_basic.jsonl

10장과 11장까지 따라간다면 다음 세 줄을 이어서 실행합니다.

python ch10/load_tax.py --embed     # 5. 세무 문서·정형 데이터 적재와 임베딩
python ch10/tax_pipeline.py --eval-all   # 6. 세무 질문 10개를 세 구성으로 채점
python ch11/export_okf.py okf_bundle     # 7. 의미 모델을 OKF 번들로 내보내기

정형 데이터 적재를 1장 실습보다 먼저 두는 이유는, 1장의 기본 RAG는 정형 데이터를 쓰지 않지만 이후 모든 구성이 쓰기 때문에 한 번 해 두면 편해서입니다. 적재 스크립트는 테이블을 지우고 다시 만들므로 여러 번 실행해도 됩니다.

실측한 적재 결과입니다.

customers       14 rows
subscriptions   14 rows
payments        17 rows
usage_stats     13 rows
incidents        3 rows
team_members     9 rows

usage_stats가 13행인 것은 01-3에서 말한 대로 C007의 사용량을 일부러 뺐기 때문입니다. 적재 직후 다음 조회로 조인이 의도대로 되는지 확인했습니다.

select s.subscription_id, p.paid_at, p.amount, u.docs_created, u.logins
from subscriptions s
join payments p on p.subscription_id = s.subscription_id
              and p.paid_at = s.current_period_start
left join usage_stats u on u.subscription_id = s.subscription_id
                       and u.period_start = s.current_period_start
where s.customer_id in ('C001','C004','C007')
order by 1;

S001  2025-09-05   19900   0     2
S004  2025-06-20  179000  40    88
S007  2025-09-02   19900  None  None

S007의 사용량이 None(NULL)으로 나옵니다. 7장의 규칙 평가는 이 NULL을 "미확인"으로 다루어 판단을 보류합니다.

결과 폴더

채점 결과는 results 폴더에 구성 이름별 JSONL 파일로 쌓입니다. 한 줄이 질문 하나이고, 답변·검색된 청크·채점 결과·토큰·소요 시간이 들어 있습니다. 이 폴더는 .gitignore에 있어 저장소에 올라가지 않습니다. 독자의 실행 결과와 책의 결과가 섞이지 않게 하기 위해서입니다. 책에 실은 결과표는 부록 B에 별도로 옮겨 두었습니다.

초기화

처음부터 다시 하고 싶을 때는 다음을 지웁니다.

대상 방법
데이터베이스 전체 (내장) 프로세스 종료 후 pgdata 폴더 삭제
데이터베이스 전체 (Docker) docker compose down -v
특정 테이블만 해당 장의 스키마 SQL을 다시 실행 (DROP TABLE IF EXISTS 포함)
채점 결과 results 폴더 삭제

정리

  • 저장소는 공통 모듈 3개, 공유 데이터 폴더, 장별 코드 폴더로 이루어지며 데이터는 모든 구성이 공유합니다.
  • 4·5장의 산출물은 YAML 파일이고 6·7·9장이 같은 파일을 각기 다른 형태로 씁니다.
  • 실행 순서는 환경 확인 → 정형 데이터 적재 → 구성 1 인덱스 → 채점입니다.
  • 다음 절에서 채점기의 동작을 봅니다.
