표준이 해결하는 문제: 교환·상호운용·추론

이 책은 지금까지 온톨로지를 YAML 파일과 PostgreSQL 테이블로 다뤘습니다. 온톨로지 교과서를 펴면 그 자리에 RDF·OWL·SPARQL이 있습니다. 둘 중 하나가 틀린 것이 아닙니다. 표준은 특정한 문제를 풀기 위해 만들어졌고, 그 문제가 우리에게 있는지가 판단의 전부입니다.

표준이 푸는 문제는 세 가지로 요약됩니다. 첫째, 교환입니다. 우리 팀이 만든 "구독" 개념을 다른 회사나 공공기관의 시스템이 읽어야 한다면, 개념과 관계를 적는 공통 문법이 필요합니다. 둘째, 상호운용입니다. 여러 시스템이 같은 개념을 가리킬 때 이름 충돌 없이 "같은 것"임을 보장하려면 전 세계에서 유일한 식별자가 필요합니다. 셋째, 추론입니다. "장애는 서비스 중단의 하위 개념"이라고 선언해 두면 서비스 중단을 묻는 질의에 장애가 자동으로 포함되도록, 정의로부터 새 사실을 기계적으로 끌어내는 규칙이 필요합니다.

노트클라우드에는 이 세 문제가 없거나 작습니다. 모델을 읽는 시스템은 우리 파이프라인 하나이고, 개념 이름은 한 팀이 정하며, 하위 개념은 두 단계뿐입니다. 그래서 이 책은 표준 없이 진행했습니다. 그렇더라도 표준이 무엇인지는 정확히 알아 두어야 합니다. 나중에 세 문제 중 하나가 생겼을 때 무엇을 가져올지 판단해야 하고, 그래프 DB 논의에서 이 용어들이 계속 등장하기 때문입니다.

RDF·OWL·SPARQL 최소 소개

자원 기술 프레임워크(Resource Description Framework, RDF)는 모든 사실을 주어·서술어·목적어 세 조각, 즉 트리플(triple)로 적는 데이터 모델입니다. "6조 1항은 4조를 준용한다"는 (6조 1항, 준용한다, 4조) 한 줄이 됩니다. 06-1의 선택지 B에서 본 개체·관계 범용 테이블이 바로 이 모양이었습니다. 세 자리에 올 수 있는 것이 각각 정해져 있습니다. 서술어는 반드시 국제화 자원 식별자(Internationalized Resource Identifier, IRI)입니다. 흔히 URI라고 부르는 그 주소입니다. 주어는 IRI이거나 빈 노드(blank node)입니다. 목적어는 IRI, 빈 노드, 리터럴(literal) 셋 중 하나이고, "30일"이나 "2025-07-01" 같은 값이 리터럴입니다. 빈 노드는 이름을 붙이지 않은 자원으로, "금액과 통화를 함께 묶은 어떤 값"처럼 따로 식별자를 줄 필요가 없는 중간 마디를 표현할 때 씁니다(W3C RDF 1.1 Concepts). 리터럴은 목적어 자리에만 올 수 있다는 점이 SQL의 값과 다른 지점입니다. RDF를 사람이 읽기 좋게 적는 문법이 Turtle이고, 아래 예시는 Turtle입니다.

RDF 스키마(RDF Schema, RDFS)와 웹 온톨로지 언어(Web Ontology Language, OWL)는 그 트리플 위에서 "이런 유형이 있고 이런 관계가 허용된다"를 선언하는 어휘입니다. 02-1에서 온톨로지의 구성 요소로 든 개념·관계·제약이 각각 클래스(class), 속성(property), 그리고 공리(axiom)와 제약(restriction)에 대응합니다. OWL은 여기에 "이 관계는 전이적이다", "이 두 클래스는 겹치지 않는다" 같은 논리적 성질을 덧붙여 추론기(reasoner)가 새 사실을 끌어낼 수 있게 합니다.

SPARQL은 RDF 데이터를 질의하는 언어입니다. SQL과 비슷하게 SELECT와 WHERE를 쓰되, WHERE 안에는 테이블 조인 대신 트리플 패턴을 적습니다. 1.1 버전부터 속성 경로(property path)가 들어와, 관계를 한 번 이상 반복해 따라가는 탐색을 한 줄로 적을 수 있습니다. 09-2의 재귀 CTE가 하는 일이 SPARQL에서는 기호 하나로 표현됩니다.

이 책의 모델을 RDF로 옮겨 보기

model.yaml의 개념 세 개(Subscription, Clause, PolicyVersion)와 관계 두 개(part_of, applies_mutatis_mutandis)를 Turtle로 옮기면 다음과 같습니다. 개념 정의 문장은 model.yaml의 것을 그대로 썼습니다.

@prefix nc:   <https://example.org/notecloud/ontology#> .
@prefix doc:  <https://example.org/notecloud/clause/> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix owl:  <http://www.w3.org/2002/07/owl#> .

# 개념 → OWL 클래스
nc:Subscription a owl:Class ;
    rdfs:label "구독"@ko ;
    rdfs:comment "고객이 특정 요금제를 특정 결제 주기로 이용하는 계약. 결제 완료 시점에 성립한다."@ko .
nc:Clause        a owl:Class ; rdfs:label "조항"@ko .
nc:PolicyVersion a owl:Class ; rdfs:label "규정 판"@ko .

# 관계 → 객체 속성 (정의역·치역이 model.yaml 의 from·to)
nc:partOf a owl:ObjectProperty ;
    rdfs:label "속한다"@ko ;
    rdfs:domain nc:Clause ; rdfs:range nc:PolicyVersion .
nc:appliesMutatisMutandis a owl:ObjectProperty ;
    rdfs:label "준용한다"@ko ;
    rdfs:domain nc:Clause ; rdfs:range nc:Clause .

# 사실 → 트리플 (clause_links.yaml 의 두 줄)
doc:refund_policy_v2_6_1 a nc:Clause ;
    nc:partOf doc:refund_policy_v2 ;
    nc:appliesMutatisMutandis doc:refund_policy_v2_3 , doc:refund_policy_v2_4 .

세 부분이 6장 스키마와 일대일로 대응합니다. 클래스 선언은 concepts 테이블의 한 행, 객체 속성 선언은 relation_types 테이블의 한 행, 마지막 사실은 clause_links 테이블의 두 행입니다. 저장 형식이 바뀌었을 뿐 담긴 내용은 같습니다. 이것이 02-4에서 "지식 그래프는 관계 테이블로도 저장할 수 있다"고 말한 근거입니다.

같은 데이터에 "학생 요금제 6조 1항이 결국 어떤 조항을 적용받는가"(Q09)를 SPARQL로 물으면 다음과 같습니다.

PREFIX nc:  <https://example.org/notecloud/ontology#>
PREFIX doc: <https://example.org/notecloud/clause/>

SELECT ?applied
WHERE {
  doc:refund_policy_v2_6_1 nc:appliesMutatisMutandis+ ?applied .
}

서술어 뒤의 더하기 기호가 속성 경로입니다. "준용 관계를 한 번 이상 따라간 끝에 닿는 모든 조항"을 뜻하며, 준용이 다시 준용을 가리키는 사슬이 있어도 길이를 지정하지 않고 끝까지 갑니다. 09-2의 재귀 CTE가 WITH RECURSIVE와 UNION ALL, 순환 방지 조건까지 열 줄 남짓으로 적는 일을 기호 하나로 대신합니다. 표현력의 차이는 분명히 있습니다. 다만 이 차이가 새 저장소와 새 언어를 팀에 들일 만큼 큰지는 별개의 문제입니다.

추론기가 필요한 조건

OWL의 가장 큰 약속은 추론입니다. 추론기가 실제로 값을 하는 상황은 세 가지입니다.

첫째, 하위 클래스의 전이입니다. Outage와 PlannedMaintenance를 Incident의 하위 클래스로 선언하면, Incident를 묻는 질의에 두 하위 유형의 개체가 자동으로 포함됩니다. 계층이 대여섯 단계이고 클래스가 수백 개면 이 자동화가 큽니다.

둘째, 역관계와 전이 관계입니다. cites의 역관계를 citedBy로 선언하면 한쪽만 저장해도 반대 방향 질의가 성립하고, supersedes를 전이적이라고 선언하면 3판이 2판을, 2판이 1판을 대체할 때 3판이 1판을 대체한다는 사실이 저장 없이 도출됩니다.

셋째, 일관성 검사입니다. RefundRequest와 CancellationRequest를 서로소(disjoint)로 선언해 두면, 어떤 요청이 두 클래스에 동시에 속하는 순간 추론기가 모순을 보고합니다. 04-2에서 "구독 취소"라는 말이 해지와 환불 중 어느 쪽인지 갈렸던 문제를, 모델 차원에서 잡아 주는 장치입니다.

노트클라우드에서 이 셋이 재귀 CTE와 코드로 충분했던 이유는 규모 때문입니다. 클래스 계층은 두 단계라 concepts 테이블의 parent_id 열 하나로 끝났고, 역관계는 clause_links의 to_ref 열에 인덱스를 걸어 조인 방향을 바꾸는 것으로 해결됐으며, 전이 관계는 09-2의 재귀 CTE가 처리했습니다. 일관성 검사는 CHECK 제약과 적재 스크립트의 검증으로 대신했습니다. 추론기가 빛나는 것은 이 넷 중 어느 하나라도 손으로 쓰기 벅찬 규모가 될 때입니다.

주의할 점이 하나 있습니다. OWL은 열린 세계 가정(open world assumption)을 따릅니다. 데이터에 없는 사실은 거짓이 아니라 "모른다"입니다. 05-4에서 "사용량 기록이 없으면 미사용이 아니라 미확인"이라고 정한 것과 방향이 같아 반가울 수 있지만, 반대로 OWL의 기수 제약(cardinality restriction)은 DB의 NOT NULL처럼 데이터를 거부하지 않습니다. "구독은 결제를 하나 이상 가진다"고 선언해도 결제 없는 구독은 오류가 아니라 "아직 모르는 결제가 있을 것"으로 해석됩니다. 데이터 검증 용도로는 별도 표준인 SHACL(Shapes Constraint Language)이 쓰이며, 이 구분을 모르면 OWL을 스키마 검증기로 오해하게 됩니다.

표준 도입의 비용

비용 항목 내용 노트클라우드 규모에서의 체감
학습 Turtle·SPARQL 문법, OWL의 논리 의미, 열린 세계 가정. SQL 개발자에게는 사고방식 전환 팀원 한 명이 수 주
도구 트리플 저장소(Apache Jena, RDF4J, GraphDB 등)와 추론기를 별도 운영. 백업·모니터링 추가 PostgreSQL 한 대에서 두 시스템으로
정형 데이터 연결 결제·사용량은 여전히 관계형. 트리플로 복제하거나 매핑 계층(R2RML 등)을 유지 이중 관리가 가장 큰 부담
모델 유지 개념 하나를 바꿀 때 YAML 한 줄이 아니라 IRI·공리·추론 결과까지 점검 04-4의 검수 절차가 두 배

표준이 값을 하는 조건을 뒤집어 말하면 도입 시점이 보입니다. 외부 기관과 모델을 주고받아야 할 때, 이미 공개된 표준 온톨로지(금융의 FIBO, 의료의 SNOMED CT, 웹의 schema.org 등)를 재사용해야 할 때, 여러 팀이 수백 개 클래스를 함께 유지해야 할 때, 그리고 일관성 검사가 사람의 검수를 대체할 만큼 모델이 커졌을 때입니다. 이 중 어느 것도 아니라면 YAML과 PostgreSQL로 시작한 지금의 방식이 손해가 아닙니다. 더 나아가 표준 기반 구현을 배우고 싶은 독자를 위한 도구와 자료는 부록 D에 정리했습니다.

정리

  • RDF는 사실을 트리플로 적는 데이터 모델, OWL은 그 위의 클래스·속성·공리 어휘, SPARQL은 질의 언어입니다. 셋은 교환·상호운용·추론이라는 문제를 풀기 위해 만들어졌습니다.
  • 이 책의 model.yaml과 clause_links는 Turtle로 그대로 옮겨집니다. 저장 형식이 다를 뿐 내용은 같습니다.
  • 추론기는 깊은 클래스 계층, 역관계·전이 관계의 자동 도출, 일관성 검사에서 값을 합니다. 노트클라우드 규모에서는 parent_id 열, 인덱스, 재귀 CTE, CHECK 제약으로 충분했습니다.
  • OWL은 열린 세계 가정을 따르므로 데이터 검증기가 아닙니다. 검증은 SHACL의 몫입니다.
  • 도입 비용의 핵심은 학습보다 정형 데이터와의 이중 관리입니다. 외부 교환·표준 온톨로지 재사용·대규모 다팀 유지가 필요해질 때 재검토하고, 그때의 학습 경로는 부록 D를 참고하세요.
