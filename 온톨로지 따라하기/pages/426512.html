[검증] 규칙 평가·조회는 PostgreSQL 16.2 실측 기준 (ontology-tutorial ch07/rules.py, ch07/pipeline.py) · LLM 답변 생성은 07-5에서 실측

분석 결과가 나오면 파이프라인은 조회하고, 규칙을 평가하고, 근거를 모읍니다. 이 절에서는 그 세 가지가 어떤 순서로 어떤 데이터를 주고받는지, 벡터 검색과 SQL이 각각 무엇을 맡는지, 규칙을 코드로 둘지 LLM에 맡길지, 실패했을 때 어디로 되돌아가는지를 봅니다. 규칙 평가는 LLM 없이 실행할 수 있어서 이 절의 결과는 모두 실측입니다.

단계별 흐름

질문 ──▶ [1] 분석 (LLM, 07-1) ──▶ 분석 JSON
                                      │
                ┌─────────────────────┼─────────────────────┐
                ▼                     ▼                     ▼
   [2a] 정형 조회 (SQL)     [2b] 규칙 평가 (코드)      [2c] 검색 (벡터+키워드)
   customer_context         evaluate_refund 등          규정 질문일 때만
   incident, ...            → Verdict                    hybrid_search
                │                     │                     │
                └─────────────────────┼─────────────────────┘
                                      ▼
                       [3] 근거 확장: 근거 조항 ID → 본문, 준용 링크 따라가기
                                      ▼
                       [4] 컨텍스트 조립 (07-3) ──▶ [5] 답변 생성 (LLM, 07-4)

정형 데이터가 필요한 질문(환불, 좌석, 장애, 영향 범위)은 2a와 2b를 거치고 2c를 거치지 않습니다. 근거 조항은 규칙이 직접 지목하기 때문에 검색이 필요 없습니다. 규정 설명 질문(Q01, Q02, Q05 등)은 2c만 거칩니다.

벡터 검색과 SQL의 역할 분담

질문 필요한 것 담당
규정이 무엇인가 (Q01, Q05, Q07) 관련 조항 본문 검색
이 고객은 어떤 상태인가 (Q11~Q24) 결제일, 금액, 사용량, 계정 상태 SQL
이 조항이 준용·대체·인용하는 것은 (Q09, Q30) 링크 SQL (링크 테이블)
어느 판이 적용되는가 (Q14, Q15) 유효기간 SQL

검색은 "무엇이 적혀 있는가"를 찾고, SQL은 "무엇이 사실인가"와 "무엇이 무엇과 연결되는가"를 찾습니다. 기본 RAG는 이 모든 것을 검색 하나로 하려 했고, 그래서 데이터 문제(D)와 규칙 문제(K)에서 틀렸습니다.

규칙을 코드로 둘지 LLM에 맡길지

5장의 rules.yaml을 실행하는 방법은 둘입니다. LLM 프롬프트에 규칙 문장을 넣고 판단을 맡기거나, 코드로 옮겨 계산하고 결과만 LLM에 주는 것입니다. 이 책은 후자를 택했습니다.

기준 프롬프트에 규칙 코드로 규칙
날짜·금액 계산 틀리기 쉬움 (일할 계산, 할인 환수) 정확
재현성 실행마다 달라질 수 있음 항상 같음
조건 누락 시 대개 단정함 requires 검사로 보류
규칙 변경 프롬프트 수정 코드 수정 + 테스트
규칙이 많아질 때 프롬프트가 길어지고 충돌 처리 불안정 우선순위·예외를 명시적으로
설명 가능성 왜 그렇게 판단했는지 추적 어려움 rules_fired와 notes로 추적

코드로 옮긴 결과가 rules.py입니다. rules.yaml의 규칙 ID와 근거 조항을 그대로 쓰므로 두 파일은 같은 것을 다른 형태로 표현한 것입니다.

# ch07/rules.py 발췌 — 규칙이 발동하면 근거 조항이 자동으로 쌓인다
def fire(self, rule_id: str, note: str | None = None) -> None:
    self.rules_fired.append(rule_id)
    for e in ev(rule_id):          # rules.yaml 의 evidence
        if e not in self.evidence:
            self.evidence.append(e)
    if note:
        self.notes.append(note)

규칙 평가 실측

규칙 평가는 LLM 없이 돌아가므로 정형 데이터가 필요한 질문 전부를 미리 검증했습니다. 출력의 일부입니다.

정형 데이터가 필요한 질문 19개의 규칙 평가 결과가 모두 질문 세트의 정답과 일치했습니다. 금액이 있는 질문(Q14 131,332원, Q17 607,838원, Q25 829원)도 오차 없이 맞았습니다.

금액이 1원 단위까지 맞으려면 반올림 시점을 정해 두어야 합니다. 이 책의 정책은 중간값(일할 금액, 할인 환수액)은 실수로 그대로 두고 최종 환불액만 한 번 반올림하는 것입니다. 설명 문장에 찍히는 중간값은 표시용으로만 반올림하고 계산에는 반올림 전 값을 씁니다. Q17(C005)이 그 차이가 드러나는 예입니다. 최종값만 반올림하면 607,838원, 중간값을 각각 반올림한 뒤 빼면 607,839원으로 1원이 어긋납니다. 정답은 607,838원이며 같은 문장을 prorate 함수 주석에도 적어 두었습니다.

유리한 규정 적용의 구현을 보면, 판을 하나 고르는 것이 아니라 두 판으로 각각 계산해 비교합니다.

두 가지 모드: 구성 3과 구성 4의 경계

rules.py에는 policy_mode 인자가 있습니다. 8장의 비교를 위해 "규칙은 있지만 의미 모델은 없는" 구성 3과, 의미 모델까지 있는 구성 4를 같은 코드로 만들기 위해서입니다.

기능 current (구성 3) versioned (구성 4) 근거가 되는 의미 모델 요소
날짜·금액 계산, 제외 조건 있음 있음 (규칙 층)
결제일로 판 선택 없음 (항상 현재 판) 있음 policy_versions, governed_by
유리한 규정 비교 없음 있음 약관 9조 3항 링크
준용 관계 없음 있음 applies_mutatis_mutandis
사용량 미확인 시 미사용으로 취급 보류 Unused 개념의 정의, requires
요청자 역할 미확인 시 진행 예상액은 계산하되 "관리자 확인 필요"를 미확인 사항으로 표시 (구성원이 요청한 것이 확인되면 보류) requested_by 관계

같은 C007을 두 모드로 평가한 실측 결과입니다.

C007 versioned: [hold] 판단 보류: 사용량 확인 필요
C007 current  : 전액 환불

구성 3은 "기록 없음"을 "사용 안 함"으로 읽어 전액 환불이라고 단정합니다. 02-2에서 말한 닫힌 세계 가정의 오답이 코드에서 그대로 재현됩니다. 이 차이가 의미 모델의 효과이고, 8-4에서 정답률로 확인합니다.

실패 시 되돌아가는 경로

실패 처리는 "코드에 있는 분기"와 "설계 목표로만 적어 둔 것"을 나누어 보아야 합니다. 섞어 읽으면 구현되지 않은 안전장치를 있다고 믿게 됩니다. 먼저 구현된 분기입니다.

실패 코드의 처리 위치
분석이 ambiguous 조회 없이 확인 요청 (status=hold) pipeline.decide
결제 취소인데 경과 시간이 null 결제 시각 확인을 요구하는 보류 pipeline.decide
requires 항목이 None (사용량 미확인 등) 규칙이 hold를 돌려줌 (versioned 모드) rules.evaluate_refund
팀 요금제를 관리자가 아닌 사람이 요청 처리 불가로 보류 rules.evaluate_refund
규칙이 예외를 냄 채점기가 오류를 결과로 기록하고 다음 질문으로 (03-4) evaluate.run

아직 구현하지 않은 것, 즉 설계 목표입니다.

실패 지금 실제로 일어나는 일 목표
고객 ID는 뽑았지만 해당 고객 데이터가 없음 customer_context가 None이라 규칙 분기에 걸리지 않고 verdict=None으로 떨어져, 일반 검색·답변 생성 경로로 갑니다 "고객 정보를 찾을 수 없음"을 명시한 보류
장애 ID·날짜로 장애를 찾지 못함 마찬가지로 verdict=None이 되어 일반 경로로 갑니다 어떤 장애인지 되묻는 보류
규정 질문에서 검색 결과가 비었음 빈 근거 그대로 답변 생성을 호출합니다. "자료만 근거로 답하라"는 프롬프트 지시에 기대고 있을 뿐, 코드가 막지는 않습니다 근거가 0건이면 생성을 건너뛰고 "관련 조항을 찾지 못했다"로 응답

미구현의 원인은 하나입니다. verdict=None이 "규정 설명 질문"과 "규칙 분기에 걸리지 않은 질문"을 함께 뜻하고, 코드가 둘을 구분하지 않습니다. 두 상태를 나누고 후자에 보류를 붙이는 것이 다음 개선 과제입니다. 목표는 모든 실패 경로가 "단정하지 않는다"로 수렴하는 것입니다. 틀린 답보다 보류가 낫다는 것이 고객지원 업무의 요구이기 때문입니다.

정리

  • 파이프라인은 분석 → 정형 조회·규칙 평가 또는 검색 → 근거 확장 → 컨텍스트 조립 → 답변 생성의 순서입니다.
  • 검색은 "무엇이 적혀 있는가", SQL은 "무엇이 사실이고 무엇과 연결되는가"를 맡습니다.
  • 규칙은 코드로 평가하며, 정형 데이터가 필요한 질문 19개의 평가 결과가 정답과 모두 일치했습니다.
  • policy_mode로 구성 3과 구성 4를 가르며, 그 차이는 판 선택·유리한 규정·준용·보류입니다.
  • 다음 절에서 이 결과를 LLM에 어떻게 전달할지 컨텍스트를 설계합니다.
