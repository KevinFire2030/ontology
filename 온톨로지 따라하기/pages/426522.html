[검증] ontology-tutorial 구성 1~4 각 3회 실행의 토큰·시간 측정 기준 · 구축 작업량은 이 책의 집필 과정 기준 · 수치는 모델·환경에 따라 달라지므로 경향에 주목

정답률만으로 구성을 고르면 안 됩니다. 구성 4는 가장 많이 맞혔지만 호출을 두 번 하고 토큰을 두 배 씁니다. 그리고 실행 비용보다 큰 것이 만들고 유지하는 비용입니다. 이 절에서는 토큰과 응답 시간, 구축과 유지에 든 작업, 규정이 바뀔 때의 수정 범위를 나란히 놓고 종합 판단표를 만듭니다.

토큰과 응답 시간

30개 질문 1회 실행의 평균입니다(3회 평균).

구성 LLM 호출 토큰 (프롬프트+완성) 소요 시간 질문당
1 기본 RAG 30 42,667 103초 1,422 토큰 / 3.4초
2 검색 개선 30 37,560 87초 1,252 토큰 / 2.9초
3 데이터+규칙 30 38,656 71초 1,289 토큰 / 2.4초
4 의미 모델 60 75,549 200초 2,518 토큰 / 6.7초

세 가지가 눈에 띕니다.

  • 구성 2와 3은 구성 1보다 싸고 빠릅니다. 조항 단위 검색은 500자 청크보다 짧은 컨텍스트를 만들고, 규칙이 계산을 끝내 주면 LLM의 답변도 짧아집니다. 정답률이 오르면서 비용이 내려간 구간입니다.
  • 구성 4는 두 배입니다. 분석 호출이 하나 더 있고, 용어 사전 전체가 분석 프롬프트에 들어가며, 답변 프롬프트에 개념 정의와 계산 과정이 더해집니다. 질문당 6.7초는 대화형 서비스에서 체감되는 지연입니다.
  • 소요 시간의 대부분은 모델의 응답 시간입니다. 데이터베이스 조회·규칙 평가·근거 확장을 합쳐도 질문당 0.4초 안팎(내장 PostgreSQL 기준 실측)이었습니다. 지연을 줄이려면 호출 수를 줄여야 하며, 분석 단계를 더 작은 모델로 돌리거나 정규식으로 대체할 수 있는 요청 종류를 먼저 걸러내는 방법이 있습니다.

토큰을 정답으로 나누면 구성 4는 정답 하나에 약 2,700토큰, 구성 3은 약 1,700토큰입니다. 구성 4에서 새로 안정 정답이 된 네 질문이 그 차액을 정당화하는지는 그 질문들이 업무에서 얼마나 비싼지에 달려 있습니다(08-5).

구축 작업량

이 책을 쓰면서 각 구성을 만드는 데 실제로 든 것을 정리했습니다. 시간은 저자 한 사람 기준의 대략적인 감각이며 독자의 숙련도에 따라 다릅니다.

구성 새로 만든 것 코드 규모 데이터 준비
1 청킹, 임베딩 테이블, 검색, 프롬프트 약 120줄 문서 6종
2 조항 분해 파서, 하이브리드 검색, 유효기간 필터 약 150줄 추가 문서 프런트매터(유효기간)
3 정형 스키마, 적재, 고객 조회, 규칙 코드, ID 정규식 약 450줄 추가 CSV 6종, 가격표
4 개념·관계·용어·링크 테이블, 조회 API, 분석 프롬프트, 판 선택·보류 규칙, 답변 형식 약 680줄 추가 model.yaml, glossary.yaml, rules.yaml, clause_links.yaml

코드 줄 수보다 무거운 것은 데이터 준비입니다. 구성 4의 YAML 네 파일은 4·5장 두 장을 들여 만든 것이고, 그 작업의 대부분은 코딩이 아니라 "이 말이 무슨 뜻인가", "이 조항이 무엇을 준용하는가"를 읽고 정하는 일이었습니다. 개념 17개, 관계 13개, 용어 10개, 링크 56개를 정하는 데 든 시간이 코드 680줄보다 길었습니다. 이 작업은 도메인을 아는 사람이 해야 하며, 개발자만으로는 되지 않습니다(11-4).

규정이 바뀔 때의 수정 범위

가상의 개정을 하나 놓고 각 구성에서 무엇을 고쳐야 하는지 비교합니다. "연간 구독 전액 환불 기간을 30일에서 45일로 늘리는 3판 시행"입니다.

구성 고칠 것 위험
1 3판 문서를 추가하고 재임베딩 1판·2판·3판 청크가 함께 검색되어 혼동 증가. 2판 문서를 빼면 과거 결제 질문에 답 못 함
2 3판 문서 추가, 프런트매터에 유효기간, 2판 valid_to 채움, 재임베딩 유효 판 필터가 있어 혼동은 없음. 과거 시점 질문은 여전히 못 함
3 위 + 규칙 코드의 30일 상수를 45일로 현재 규정만 아는 구성이라 3판 시행 전 결제 고객에게도 45일을 적용함(잘못)
4 위 + policy_versions 행 추가, 조항 분해(자동), supersedes 링크 추가, 규칙 코드의 판 목록·비교 분기 수정, 영향 범위 조회로 FAQ·매뉴얼 재점검 결제일로 판을 고르는 구조가 이미 있어 과거 결제 고객을 맞게 처리. 재점검 대상은 Q29·Q30 조회로 자동 산출

구성 3의 위험이 중요합니다. 규칙을 코드로 두면 계산은 정확하지만, 규정이 바뀌는 순간 "언제부터 누구에게"라는 시점 문제가 코드 상수 하나에 묻힙니다. 시점을 데이터(유효기간)로 두는 구성 4에서는 "어느 판이 언제 유효했는가"가 테이블에 있으므로 과거 결제 고객이 자동으로 맞게 처리됩니다. 이것이 06-2에서 유효기간을 테이블에 둔 이유이고, 규정 개정이 잦은 업무(10장의 세무)에서 결정적인 차이가 됩니다.

다만 구성 4에서도 개정이 데이터 추가만으로 끝나지는 않습니다. 이 책의 rules.py는 판이 1판·2판 두 개라는 전제로 짜여 있습니다. 전액 환불 기간은 판별 매개변수(FULL_REFUND_DAYS)에 있지만, 두 판을 비교해 유리한 쪽을 고르는 부분은 파이썬 분기이고 판이 셋이 되면 비교 대상을 늘려야 합니다. 정확히 말하면 이렇습니다.

3판을 더할 때 구성 4에서 하는 일
데이터로 끝나는 것 문서 추가와 프런트매터 유효기간, 2판 valid_to 채우기, 조항 분해와 임베딩(스크립트가 자동), supersedes 링크
코드를 고쳐야 하는 것 판별 매개변수에 3판 항목 추가, 유리한 판 비교를 두 판이 아닌 N판으로 일반화

판 개수에 열려 있는 규칙 평가기는 이 책의 범위를 넘습니다. 11-2에서 개정 절차를 다룰 때 이 두 가지를 구분해 적었습니다.

검수가 필요한 변경 문서 규칙 코드 개념 정의·관계·링크 (도메인 전문가 검수, 11-1)
오답이 났을 때 찾을 곳 검색 결과 검색 결과, 데이터, 규칙 위 + 분석 결과, 링크, 용어 사전

구성 4의 관리 부담은 분명히 큽니다. 다만 그 부담의 실체는 "의미를 명시적으로 적어 두는 일"이고, 그 일을 하지 않는 구성에서는 같은 의미가 개발자의 머릿속과 코드의 if 문에 흩어져 있을 뿐 사라지지는 않습니다(02-2). 부담이 늘어난 것이 아니라 보이게 된 것에 가깝습니다.

노트클라우드에 대한 이 책의 판단은 구성 4입니다. 환불 규정이 개정되었고, 준용과 예외가 있으며, 틀리면 비싼 질문이 의미 모델 없이는 풀리지 않았기 때문입니다. 그러나 규정이 거의 바뀌지 않고 질문이 데이터 조회 위주인 업무라면 구성 3에서 멈추는 것이 맞습니다. 그 판단을 실제 질문 세트로 하는 것이 이 장의 방법이고, 그 방법은 어느 구성을 택하든 같습니다.

정리

  • 구성 2·3은 구성 1보다 정확하면서 싸고 빠릅니다. 구성 4는 정확도를 더 올리지만 토큰과 시간이 두 배입니다.
  • 구축 비용의 실체는 코드가 아니라 의미를 정하는 도메인 작업입니다.
  • 규정 개정 시 구성 3은 코드 상수와 시점 오류의 위험을, 구성 4는 데이터 추가와 자동 재점검을 갖습니다.
  • 어느 구성이 맞는지는 업무의 성격과 질문 세트로 판단하며, 노트클라우드에서는 구성 4가 맞았습니다.
  • 다음 장에서 그래프 탐색이 필요한 질문과 PostgreSQL에 남을 질문을 가릅니다.
