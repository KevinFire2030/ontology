[검증] PostgreSQL 16.2 + pgvector 0.6.2 실측 기준 · LLM은 OpenAI API 기준으로 서술

01-1에서 본 오답을 직접 재현해 봅니다. 예제 저장소를 받아 기본 RAG를 만들고, 30개 질문을 자동으로 채점하고, 오답을 네 가지 유형으로 분류합니다. 이 실습의 결과가 8장 비교 실험의 첫 번째 열(구성 1)이 됩니다.

실습 환경

  • PostgreSQL 16 + pgvector (Docker 또는 내장 실행, 03-1)
  • Python 3.10 이상, OpenAI API 키 (03-2)
  • 예제 저장소 ontology-tutorial. 아직 3장을 읽지 않았다면 저장소 README의 "시작하기" 네 단계만 따라 해도 됩니다.
  • 채점 결과는 모델과 실행 시점에 따라 조금씩 다릅니다. 숫자보다 어떤 유형이 틀리는지에 주목해 주세요.

실습 1: 인덱스 만들기

python ch06/load_structured.py      # 정형 데이터 적재 (이 실습에서는 쓰지 않지만 이후 장을 위해)
python ch01/rag_basic.py --index

문서를 500자 단위로 자르고 임베딩해 chunks_basic 테이블에 넣습니다.

# ch01/rag_basic.py 발췌
def chunk_text(text: str, size: int = CHUNK_CHARS) -> list[str]:
    """문단 경계를 존중하면서 size 글자 안팎으로 자릅니다."""
    paras = [p.strip() for p in re.split(r"\n\s*\n", text) if p.strip()]
    chunks, buf = [], ""
    for p in paras:
        if len(buf) + len(p) + 1 > size and buf:
            chunks.append(buf)
            buf = p
        else:
            buf = (buf + "\n" + p) if buf else p
    if buf:
        chunks.append(buf)
    return chunks

실측 출력입니다.

faq                      2 chunks
ops_manual               4 chunks
pricing_guide            3 chunks
refund_policy_v1         3 chunks
refund_policy_v2         4 chunks
terms_of_service         3 chunks
총 19 chunks / 임베딩 토큰 6,091

문서 6종이 19개 조각이 되었습니다. 환불 규정 2판이 4조각이라는 것은 조항 하나가 어느 조각에 들어갈지 규정의 구조와 무관하게 글자 수로 정해졌다는 뜻입니다. 1판과 2판의 조각이 섞여 검색되는 원인이 여기 있습니다.

실습 2: 질문 하나 던져 보기

python ch01/rag_basic.py --ask "구독을 해지하면 남은 기간의 돈이 돌아오나요?"

# ch01/rag_basic.py 발췌
def answer(question: str, as_of: date) -> dict:
    ctx = retrieve(question)
    context_text = "\n\n".join(f"[{c['doc_id']}#{c['chunk_no']}]\n{c['content']}" for c in ctx)
    user = f"오늘 날짜: {as_of}\n\n참고 문서:\n{context_text}\n\n질문: {question}"
    text = llm.chat(SYSTEM, user)
    return {"answer": text, "contexts": [f"{c['doc_id']}#{c['chunk_no']}({c['score']})" for c in ctx]}

검색된 청크와 답변이 출력됩니다. 실측에서 검색된 청크는 다음과 같았습니다.

검색된 청크: ['refund_policy_v2#1(0.42)', 'refund_policy_v1#1(0.387)', 'ops_manual#3(0.345)', 'refund_policy_v1#2(0.342)', 'refund_policy_v2#2(0.334)']

약관 4조(해지·환불·결제 취소의 구분)는 없습니다. 유사도 점수도 0.42 이하로 낮습니다. 질문의 "해지"와 "돈이 돌아오나요"가 약관의 문장과 표현이 다르기 때문입니다. 이 상태로 LLM에 넘기면 01-1의 오답 1이 나옵니다.

핵심어 정비는 구성 1~3의 첫 실행 결과를 훑은 뒤 한 차례 더 했고(8-1), 그 뒤에는 기준을 고정해 모든 구성을 같은 기준으로 재채점했습니다. 구성 1의 최종 정답 수는 11개입니다.

실습 4: 오답 분류하기

결과 파일을 열어 오답마다 01-2의 진단표를 채웁니다. 다음 스크립트가 오답과 검색된 청크를 나란히 보여 줍니다.

import json
rows = [json.loads(l) for l in open("results/config1_basic.jsonl", encoding="utf-8")]
for r in rows:
    if not r["correct"]:
        print(r["id"], r["error_type"], r["contexts"])
        print(r["answer"][:300])
        print()

분류할 때 던지는 질문은 01-2의 순서 그대로입니다. 정답 조항을 직접 넣어 주면 맞힐까(R), 정형 데이터가 필요한가(D), 단어의 뜻이나 개념 관계가 문제인가(M), 조건·시점 판단이 빠졌나(K). 실측에서 나온 분류는 다음과 같습니다.

유형 오답 비고
데이터 D Q11, Q12, Q13, Q16, Q17, Q24, Q25, Q26, Q27, Q29 10개. 모두 "정보를 확인할 수 없다"거나 일반론으로 답함
규칙 K Q14, Q15, Q18, Q19, Q21 5개. 판 선택, 계산, 예외, 보류의 질
의미 M Q03, Q09, Q20 3개. 해지≠환불, 준용
검색 R Q30 1개. 인용 관계

재채점 전에는 Q07·Q10이 오답, Q24가 정답이었습니다. 정답 쪽도 한 번 훑어보는 습관이 이런 경우를 잡아냅니다.

관찰 포인트

  • 데이터 문제가 가장 많습니다. 11개 중 10개가 틀렸고, 맞은 1개(Q23)도 문서의 일반 규정(관리자만 요청 가능)으로 답한 것입니다. 이 유형은 검색을 아무리 개선해도 풀리지 않습니다.
  • 규칙 문제는 반쯤 맞습니다. Q02, Q06, Q08, Q10, Q22, Q28처럼 규정 문장 자체에 답이 있는 질문은 맞히고, Q14·Q15처럼 계산이나 판 비교가 필요한 질문은 틀립니다.
  • 의미 문제는 검색 점수가 낮습니다. Q03의 검색 점수가 0.42 이하였습니다. 질문의 단어와 문서의 단어가 다르다는 신호가 점수에 드러납니다.
  • 채점은 거칩니다. Q07·Q10은 맞았는데 오답, Q24는 못 맞혔는데 정답으로 처리되었습니다. 규칙 채점의 재현성과 비용을 얻는 대가입니다. 첫 실행 뒤 사람이 훑고 핵심어를 다듬는 절차를 빼면 안 됩니다.
  • 답을 못 한 것과 틀린 것을 구분해야 합니다. 데이터 문제의 답변 대부분은 "확인이 필요하다"는 안전한 응답이었습니다. 위험한 것은 Q03처럼 다른 개념의 규정으로 단정하는 답입니다.

더 해 보기

  • 청크 크기를 200자와 1,000자로 바꿔 채점해 보세요. 어떤 유형의 정답률이 움직이고 어떤 유형은 그대로인지 확인합니다.
  • 검색 상위 개수를 5에서 10으로 늘려 보세요. 토큰은 얼마나 늘고 정답은 얼마나 느는지 봅니다.
  • 시스템 프롬프트에 "해지와 환불은 다르다"는 한 문장을 넣고 Q03만 다시 실행해 보세요. 그것이 4장에서 만드는 용어 사전의 가장 작은 형태입니다.

정리

  • 기본 RAG는 30개 중 11개를 맞혔고, 데이터 문제 10개·규칙 문제 5개·의미 문제 3개·검색 문제 1개가 틀렸습니다.
  • 오답 대부분은 문서에 없는 것을 요구한 것이며, 문서를 더 넣어도 풀리지 않습니다.
  • 다음 장에서 이 오류 중 어느 것에 온톨로지가 필요하고 어느 것은 다른 방법으로 충분한지 따져 봅니다.
