[검증] PostgreSQL 16.2 + pgvector 0.6.2 실측 기준 (임베딩 저장은 OpenAI API 기준으로 서술)

답변에 근거를 붙이려면 근거의 단위가 있어야 합니다. 1장의 기본 RAG는 문서를 500자 단위로 잘랐고, 그 조각은 사람이 인용할 수 있는 단위가 아니었습니다. 이 절에서는 문서를 조·항 단위로 나누어 조항 테이블에 넣고, 조항 사이의 관계를 간선 테이블에 넣고, 조항 본문의 임베딩을 같은 테이블에 두어 벡터 검색과 관계 조회를 한 번에 할 수 있게 만듭니다.

조항 테이블

CREATE TABLE clauses (
    clause_id  text PRIMARY KEY,                   -- 'refund_policy_v2:4.2'
    doc_id     text NOT NULL REFERENCES policy_versions,
    clause_no  text NOT NULL,                      -- '4.2' / '4' / '결제와 구독'
    heading    text,
    content    text NOT NULL,
    embedding  vector(1536)
);

조항 ID는 5-3에서 정한 형식 그대로입니다. 문서 ID와 조·항 번호를 콜론으로 잇습니다. 이 ID가 곧 인용 표기이므로, 질문 세트의 evidence, 규칙 파일의 evidence, 링크 파일의 from·to가 모두 같은 문자열을 씁니다. 한 곳에서 정한 ID 체계를 네 곳이 공유하는 것이 근거 연결의 전부입니다.

문서를 조항으로 나누기

적재 스크립트가 마크다운을 읽어 조항을 만듭니다. 문서 종류에 따라 나누는 단위가 다릅니다.

문서 구조 조항 단위 예
환불 규정, 약관 "제N조 (제목)" 아래 번호 항 조 전체 + 항 각각 refund_policy_v2:4, refund_policy_v2:4.1
운영 매뉴얼 "N. 제목" 아래 번호 항목 절 전체 + 항목 각각 ops_manual:2, ops_manual:2.2
FAQ, 요금 안내 절 제목만 절 전체 faq:결제와 구독

조 전체와 항 각각을 둘 다 넣는 이유가 있습니다. 준용 관계는 "6조 1항은 3조와 4조를 준용한다"처럼 조 단위로 걸리고, 인용은 "운영 매뉴얼 2절 2항은 약관 9조 3항을 인용한다"처럼 항 단위로 걸립니다. 두 단위가 모두 있어야 링크를 자연스럽게 표현할 수 있습니다.

# ch06/load_ontology.py 발췌
m = re.match(r"제(\d+)조\s*\((.*?)\)", head)
if m:  # 조·항 구조
    art, title = m.group(1), m.group(2)
    clauses.append({"clause_no": art, "heading": title, "content": f"제{art}조 ({title})\n{rest}"})
    for im in re.finditer(r"^(\d+)\.\s+(.*?)(?=^\d+\.\s|\Z)", rest, re.S | re.M):
        para = im.group(1)
        clauses.append({"clause_no": f"{art}.{para}", "heading": title,
                        "content": f"제{art}조 제{para}항: {im.group(2).strip()}"})

항의 본문 앞에 "제4조 제2항:"을 붙여 두는 것도 의도적입니다. 검색된 조각을 LLM에 넘길 때 그 조각이 어느 조항인지 본문 안에서도 보이게 하기 위해서입니다.

적재 결과 108개 조항이 만들어졌습니다. 조항 하나를 확인해 보면 다음과 같습니다.

refund_policy_v2:4.2 -> ('연간 구독의 환불',
  '제4조 제2항: 30일이 지난 뒤 요청하면 잔여 기간을 일할 계산하여 환불합니다.
   단, 연간 결제 할인으로 감면된 금액은 사용한 기간에 비례하여 환수합니다.')

조항 사이의 관계

CREATE TABLE clause_links (
    from_clause text NOT NULL REFERENCES clauses,
    rel         text NOT NULL CHECK (rel IN ('supersedes','applies_mutatis_mutandis','cites','defines')),
    to_ref      text NOT NULL,                     -- 조항 id 또는 'concept:ID'
    PRIMARY KEY (from_clause, rel, to_ref)
);

to_ref가 외래 키가 아닌 것은 대상이 조항일 수도 개념일 수도 있기 때문입니다. defines 관계는 조항이 개념을 정의한다는 뜻이고 대상이 "concept:Unused"처럼 개념 ID입니다. 참조 무결성은 적재 스크립트가 검사합니다. 실제로 첫 적재 때 이 검사가 잡아낸 것이 있었습니다.

경고: 존재하지 않는 조항·개념을 가리키는 링크 [{'from': 'refund_policy_v2:2.1', 'rel': 'defines', 'to': 'concept:Unused'}]

"미사용"이 용어 사전에는 있었지만 개념 목록에는 없었던 것입니다. 사용량에서 계산되는 파생 상태라 개념으로 두지 않았는데, 조항이 정의하는 대상이라면 개념이어야 합니다. model.yaml에 Unused를 파생 개념으로 추가해 해결했습니다. 적재 시 검사가 모델의 빈틈을 찾아 준 사례입니다.

적재된 링크는 56개입니다.

관계 수 뜻
supersedes 13 2판 조항이 1판 조항을 대체
applies_mutatis_mutandis 2 준용 (학생 6조 1항 → 3조, 4조)
cites 28 운영 매뉴얼·FAQ·요금 안내 항목이 근거로 삼는 조항
defines 13 조항이 개념을 정의

임베딩 저장

조항 본문의 임베딩은 같은 테이블의 embedding 컬럼에 둡니다. 적재 스크립트에 --embed 옵션을 주면 채워집니다.

# ch06/load_ontology.py 발췌
rows = conn.execute("SELECT clause_id, content FROM clauses ORDER BY clause_id").fetchall()
vecs = llm.embed([r[1] for r in rows])
for (cid, _), v in zip(rows, vecs):
    conn.execute("UPDATE clauses SET embedding=%s WHERE clause_id=%s", (v, cid))

108개 조항이므로 임베딩 비용은 무시할 수준입니다. 임베딩 없이 적재하는 옵션을 따로 둔 이유는 조항·링크·개념 테이블은 API 키 없이도 쓸 수 있어야 하기 때문입니다. 06-4의 조회 함수와 07-2의 규칙 평가는 임베딩을 쓰지 않습니다.

벡터 검색과 관계 조회를 한 쿼리로

조항 테이블에 임베딩이 있으면 유효기간 필터와 벡터 검색을 한 번에 할 수 있습니다.

SELECT c.clause_id, p.title, p.valid_from, p.valid_to, c.content,
       1 - (c.embedding <=> :qv) AS score
FROM clauses c JOIN policy_versions p USING (doc_id)
WHERE c.embedding IS NOT NULL
  AND p.valid_from <= :as_of AND (p.valid_to IS NULL OR p.valid_to >= :as_of)
ORDER BY c.embedding <=> :qv
LIMIT 8;

1장의 기본 RAG와 다른 점은 세 가지입니다. 조각이 조항 단위이고, 문서 제목과 유효기간이 함께 나오며, 기준일에 유효하지 않은 판을 걸러냅니다. 이것이 8-2에서 "검색 개선"이라고 부르는 구성 2의 전부입니다. 아직 의미 모델은 쓰지 않았습니다.

검색된 조항에 링크를 더하는 것은 그다음 단계입니다. 예를 들어 학생 요금제 질문에 6조 1항이 검색되면, 준용 링크를 따라 3조와 4조를 함께 가져옵니다. 이것은 구성 4(07-2)에서 합니다.

# ch07/pipeline.py 발췌
for cid in clause_ids:
    seen.append(cid)
    for nxt in api.linked(cid, "applies_mutatis_mutandis"):
        if nxt not in seen:
            seen.append(nxt)

임베딩 갱신 전략

조항 본문이 바뀌면 임베딩도 다시 만들어야 합니다. 규모가 작을 때는 전체를 다시 만드는 것이 가장 단순하고 안전합니다. 규모가 커지면 본문의 해시를 함께 저장해 두고 해시가 바뀐 조항만 다시 임베딩합니다. 어느 쪽이든 원칙은 같습니다. 임베딩은 본문에서 파생된 값이므로 본문이 원본이고, 임베딩이 없거나 오래되어도 조항 조회와 규칙 평가는 동작해야 합니다.

정리

  • 조항 ID 하나를 질문 세트·규칙·링크·테이블이 공유하는 것이 근거 연결의 핵심입니다.
  • 문서 종류에 따라 조 전체와 항 각각을 모두 조항으로 넣어 준용(조 단위)과 인용(항 단위)을 표현합니다.
  • 링크의 참조 무결성을 적재 시 검사하면 모델의 빈틈(정의 대상이 개념에 없음)이 드러납니다.
  • 임베딩은 조항 테이블의 컬럼이며, 유효기간 필터와 벡터 검색을 한 쿼리로 합칠 수 있습니다.
  • 다음 절에서 이 테이블들을 조회 함수로 감싸 파이프라인과 LLM이 쓰게 합니다.
