이 책의 약속은 "같은 질문을 여러 방식으로 풀어 차이를 보여 준다"입니다. 그 약속을 지키는 도구가 채점기입니다. 채점기가 흔들리면 비교가 무너지므로, 단순하고 재현 가능하게 만들었습니다. 이 절에서는 질문 세트의 형식, 채점 규칙, 구성별 결과를 한 표로 모으는 방법, 비용과 시간을 기록하는 방법을 봅니다.

파이프라인의 규약

채점기는 파이프라인의 내부를 모릅니다. 다음 형태의 함수면 무엇이든 채점할 수 있습니다.

def answer(question: str, as_of: date) -> dict:
    ...
    return {"answer": "...", "status": "answer", "evidence": [...], "contexts": [...]}
반환 키 필수 뜻
answer 예 최종 답변 문장
status 아니오 answer(결론) 또는 hold(보류·확인 요청). 없으면 answer로 간주
evidence 아니오 답변이 근거로 삼은 조항 ID 목록
contexts 아니오 검색된 청크 등 디버깅 정보

기본 RAG(구성 1)는 answer와 contexts만 돌려주고, 7장의 파이프라인은 네 가지를 모두 돌려줍니다. 규약이 얇아서 독자가 자기 파이프라인을 끼워 넣기도 쉽습니다.

채점 규칙

채점은 규칙 기반이며 네 단계입니다.

# common/evaluate.py 발췌
def grade(q: dict, answer: str) -> dict:
    a = _norm(answer or "")
    # key_facts 항목은 '표현1|표현2' 처럼 동의 표현을 '|' 로 나열할 수 있다 (하나라도 있으면 충족)
    missing = [k for k in q.get("key_facts", []) if not any(_norm(alt) in a for alt in str(k).split("|"))]
    # 금지 표현은 공백을 유지한 채 비교한다 ("환불 가능" 이 공백 제거 후 "불가능" 에 걸리는 오판 방지)
    a_sp = (answer or "").replace(",", "").lower()
    forbidden = [k for k in q.get("forbidden_facts", []) if k.replace(",", "").lower() in a_sp]
    numeric_ok = True
    if "numeric_answer" in q:
        tol = q.get("numeric_tolerance", 0)
        numeric_ok = any(abs(n - q["numeric_answer"]) <= tol for n in _numbers(answer or ""))
    correct = not missing and not forbidden and numeric_ok
    return {"correct": correct, "missing": missing, "forbidden": forbidden, "numeric_ok": numeric_ok}
  1. 핵심 사실 포함. key_facts의 모든 항목이 답변에 들어 있어야 합니다. 비교 전에 _norm이 공백과 쉼표를 제거하고 소문자로 바꾸므로 "19,900원"과 "19900 원"은 같게 취급됩니다. 한 항목을 표현1|표현2 처럼 세로줄로 나누어 적으면 동의 표현으로 보고 그중 하나만 있어도 충족으로 셉니다. 같은 사실을 "7일 이내"라고도 "7일 안에"라고도 쓸 수 있어서 둔 장치입니다.
  2. 금지 사실 부재. forbidden_facts 중 하나라도 있으면 오답입니다. Q02의 "14일이 현재 기준"처럼 그럴듯한 오답을 잡습니다. 다만 금지 표현만은 공백을 지우지 않고 비교합니다. 공백까지 지우면 정상 답변의 "환불 가능"이 금지 표현 "불가능"에 걸려 억울한 오답이 되기 때문입니다.
  3. 숫자 일치. numeric_answer가 있는 질문은 답변에 나온 숫자 중 하나가 허용 오차 안에 있어야 합니다. Q14는 131,332원에 오차 500원, Q25는 829원에 오차 5원입니다. 일할 계산은 날짜를 어떻게 세느냐에 따라 하루치가 달라질 수 있어 오차를 둡니다.
  4. 보류 판정. expected_status가 hold인 질문은 key_facts가 "확인", "사용량" 같은 확인 요청 표현으로 되어 있고, forbidden_facts가 단정 표현("전액 환불합니다")으로 되어 있어 단정하면 오답이 됩니다.

LLM을 채점자로 쓰지 않은 이유는 두 가지입니다. 실행마다 같은 결과가 나와야 여러 구성을 여러 번 비교할 수 있고, 30문항 곱하기 다섯 구성 곱하기 반복 횟수만큼의 채점 비용이 0이어야 부담 없이 돌릴 수 있습니다. 대신 규칙 채점은 표현이 다르면 맞는 답도 놓칠 수 있으므로, 결과 파일을 사람이 한 번 훑어 억울한 오답을 확인하는 절차를 8-1에 두었습니다.

실행과 기록

run() 함수가 질문 30개를 돌리고 결과를 저장합니다.

# common/evaluate.py 발췌
def run(config_name, pipeline, *, only=None, verbose=True):
    as_of, questions = load_questions()
    out_path = RESULTS_DIR / f"{config_name}.jsonl"
    llm.usage.reset()
    with out_path.open("w", encoding="utf-8") as f:
        for q in questions:
            before = llm.usage.as_dict()
            t = time.time()
            try:
                res = pipeline(q["question"], as_of)
            except Exception as e:
                res = {"answer": f"[ERROR] {e}", "status": "error"}
            elapsed = time.time() - t
            after = llm.usage.as_dict()
            g = grade(q, res.get("answer", ""))
            row = {"config": config_name, "id": q["id"], "error_type": q["error_type"],
                   "answer": res.get("answer", ""), "status": res.get("status", "answer"),
                   "evidence": res.get("evidence", []), "contexts": res.get("contexts", []),
                   **g, "seconds": round(elapsed, 2),
                   "prompt_tokens": after["prompt_tokens"] - before["prompt_tokens"],
                   "completion_tokens": after["completion_tokens"] - before["completion_tokens"],
                   "calls": after["calls"] - before["calls"]}
            f.write(json.dumps(row, ensure_ascii=False) + "\n")

질문마다 호출 전후의 usage 차이를 빼서 그 질문에 쓴 토큰과 호출 횟수를 기록합니다. 파이프라인이 예외를 내도 멈추지 않고 오류를 결과로 남깁니다. 실행 중 화면에는 질문별로 정답 여부와 소요 시간, 오답이면 누락된 핵심 사실이 표시됩니다.

구성별 결과를 한 표로

compare() 함수는 여러 구성의 결과 파일을 읽어 질문별 정답 여부를 마크다운 표로 만듭니다.

from common import evaluate
print(evaluate.compare("config1_basic", "config2_search", "config3_sql", "config4_semantic"))
질문 유형 config1_basic config2_search config3_sql config4_semantic
Q01 - O O O O
Q03 M X X X O
...
정답 수 9/30 12/30 21/30 27/30

위 표의 숫자는 형식 설명을 위한 작성 예시입니다. 이 표가 8장의 핵심 산출물이 됩니다. 어느 질문이 어느 구성에서 처음 맞기 시작했는지를 보면, 그 구성 요소가 그 오류 유형을 해결했다는 근거가 됩니다.

비용·시간 기록

토큰 수와 소요 시간은 결과 파일에 질문 단위로 남습니다. 8-6에서는 이것을 구성별로 합산해 비교합니다. 다만 두 가지를 기억해 주세요.

  • 소요 시간은 네트워크와 API 부하에 따라 흔들립니다. 절대값보다 구성 간 배율에 주목합니다.
  • 토큰 수는 프롬프트에 무엇을 넣었는지를 직접 반영합니다. 의미 모델을 프롬프트에 넣는 구성 4가 구성 1보다 토큰을 더 쓰는 것은 당연하고, 질문은 "그 토큰만큼 정답률이 올랐는가"입니다.

재채점

파이프라인을 다시 돌리지 않고 채점 규칙만 바꿔 다시 매길 수 있습니다. key_facts를 다듬은 뒤 기존 결과를 재채점할 때 씁니다.

python -m common.evaluate results/config1_basic.jsonl

정리

  • 채점기는 answer를 돌려주는 함수라면 무엇이든 받으며, 규칙 기반이라 재현 가능하고 비용이 없습니다.
  • 핵심 사실 포함, 금지 사실 부재, 숫자 오차, 보류 판정의 네 단계로 정답을 가립니다.
  • 결과는 질문 단위 JSONL로 남고, compare()가 구성별 표를 만듭니다.
  • 다음 장에서 질문 30개로부터 개념을 뽑아내는 설계 작업을 시작합니다.
