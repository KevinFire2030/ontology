규칙이 결론을 내고 근거 조항이 모였다면, 남은 일은 그것을 LLM에 넘겨 문장으로 만드는 것입니다. 무엇을 얼마나 어떤 형식으로 넣느냐가 컨텍스트 설계입니다. 이 절에서는 이 책의 파이프라인이 프롬프트에 넣는 네 가지 요소, 너무 많이 넣을 때와 너무 적게 넣을 때의 문제, 사전 조회 방식과 도구 호출 방식의 비교, 그리고 토큰 비용을 재는 방법을 봅니다.

프롬프트에 들어가는 네 가지

오늘 날짜: 2025-09-08

관련 개념 정의:                              ← (1) 개념
- 미사용(Unused): 한 결제 주기 동안 새로 생성한 문서가 0건이고 ... [정의 조항: refund_policy_v2:2.1]

근거 조항:                                   ← (2) 조항 (문서 제목·유효기간 메타데이터 포함)
[refund_policy_v2:3.1] (노트클라우드 환불 규정 (제2판), 유효 2025-07-01 ~ 현재)
제3조 제1항: 월간 구독은 결제 완료일로부터 7일 이내에 요청하고 미사용 상태인 경우 ...

규칙 판단(환불): [hold] 판단 보류: 사용량 확인 필요   ← (3) 판단 결과
적용 규정 판: refund_policy_v2
계산·적용 과정:
  - 결제 후 6일 경과로 기간 요건은 충족하나 사용량 기록이 없어 미사용 여부를 판정할 수 없습니다
미확인: 사용량(문서 생성 수·로그인 횟수)

질문: 고객 C007이 환불을 요청했습니다. 어떻게 처리하나요?    ← (4) 질문
요소 출처 왜 넣는가
개념 정의 concepts 테이블 (분석 단계가 고른 개념 ID) 답변이 용어를 정확히 쓰게 하고, 정의 조항을 인용할 수 있게
근거 조항 규칙의 evidence 또는 검색 결과 + 준용 확장 답변이 인용할 문장. 유효기간이 붙어 있어 판을 혼동하지 않음
판단 결과 rules.py의 Verdict 결론·금액·승인자·적용 판·계산 과정·미확인 사항
질문 원문

정형 데이터 자체(결제일, 사용량 수치)는 넣지 않습니다. 규칙이 이미 그 데이터로 판단을 끝냈고 계산 과정을 notes에 문장으로 남겼기 때문입니다. LLM에 원시 데이터를 주면 다시 계산하려 들고, 그 계산이 규칙과 어긋날 수 있습니다.

너무 많이 넣을 때

규정 문서 전체를 넣으면 어떻게 될까요. 노트클라우드 문서 6종은 합쳐도 수천 토큰이라 넣을 수는 있습니다. 문제는 양이 아니라 선택입니다. 1판과 2판이 함께 들어가면 LLM은 어느 판이 적용되는지 스스로 판단해야 하고, 그 판단이 규칙과 다를 수 있습니다. Q02에서 "14일"이라고 답하는 오류가 이렇게 생깁니다.

용어 사전과 개념 정의 전체를 매번 넣는 것도 같은 문제입니다. 관련 없는 정의가 많으면 답변이 그것을 인용하려 하고, 토큰이 늘고, 정작 필요한 정의가 묻힙니다. 그래서 분석 단계가 고른 개념만 넣습니다.

너무 적게 넣을 때

반대로 결론만 넣고 근거 조항을 빼면, 답변은 맞아도 인용이 없거나 지어낸 조항 번호를 씁니다. 판단 결과에서 계산 과정(notes)을 빼면 "왜 131,332원인가"를 설명하지 못합니다. 유효기간 메타데이터를 빼면 "제1판 3조 1항에 따르면 14일"이라고 현재 규정처럼 말할 수 있습니다.

기준은 "답변에 나와야 하는 모든 문장의 출처가 프롬프트 안에 있는가"입니다. 결론은 판단 결과에, 조건은 계산 과정에, 인용은 근거 조항에, 용어는 개념 정의에 있어야 합니다.

사전 조회 방식과 도구 호출 방식

의미 모델을 LLM에 전달하는 방법은 크게 둘입니다.

사전 조회 (이 책) 도구 호출 (function calling)
흐름 코드가 분석 → 조회 → 규칙 → 결과를 프롬프트에 넣음 LLM이 필요할 때 함수를 호출하며 대화를 이어감
LLM 호출 수 2회 (분석, 답변) 가변 (호출할 때마다 +1)
조회 순서 코드에 고정 LLM이 결정
재현성 높음 낮음 (호출 순서·횟수가 실행마다 다를 수 있음)
요청 종류가 많아질 때 조회 계획 코드가 커짐 도구 설명만 추가
규칙 평가 코드가 먼저 끝냄 규칙 함수를 도구로 두거나 LLM이 판단
적합한 상황 요청 종류가 정해져 있고 비교 실험이 필요할 때 요청이 열려 있고 탐색이 필요할 때

이 책이 사전 조회를 택한 이유는 8장의 비교 때문입니다. 구성 요소를 하나씩 바꿔 가며 정답률을 재려면 실행마다 같은 조회가 일어나야 합니다. 도구 호출 방식은 LLM이 어떤 도구를 몇 번 부르느냐가 실행마다 달라져 비교의 통제 변수가 흔들립니다.

다만 06-4의 함수들은 그대로 도구로 등록할 수 있게 만들어 두었습니다. 실제 서비스에서 요청 종류가 열려 있다면 도구 호출로 바꾸되, 규칙 평가 함수(evaluate_refund 등)를 도구로 노출해 계산은 여전히 코드가 하게 하는 것이 5-5의 경계를 지키는 방법입니다.

답변 프롬프트

당신은 노트클라우드 고객지원 담당자를 돕는 도우미입니다.
아래 자료(개념 정의, 근거 조항, 규칙 판단)만 근거로 한국어로 답하세요. 형식:

결론: (한두 문장. 금액·날짜는 숫자로)
적용 조건: (어떤 조건·시점·규정 판이 적용되었는지)
근거: (조항 id 를 그대로 나열)
미확인 사항: (있으면 무엇을 확인해야 하는지, 없으면 '없음')

규칙 판단이 '보류'이면 결론을 단정하지 말고 확인이 필요하다고 답하세요.
규칙 판단이 있으면 그 결과와 금액을 바꾸지 말고 문장으로 옮기세요.

마지막 두 줄이 에이전트 행동 제어입니다. 보류일 때 단정하지 말 것, 규칙의 결과와 금액을 바꾸지 말 것. LLM의 역할을 "판단"에서 "전달"로 좁히는 문장입니다. 이 문장이 없으면 LLM은 근거 조항을 읽고 스스로 다시 판단하려 하며, 그 판단이 규칙과 어긋나는 순간 파이프라인 전체가 무의미해집니다.

토큰 비용 재기

03-4의 채점기가 질문마다 프롬프트 토큰과 완성 토큰을 기록합니다. 구성 4는 분석과 답변 두 번 호출하므로 구성 1~3보다 호출 수가 두 배이고, 프롬프트에 개념 정의와 판단 과정이 더 들어가므로 토큰도 많습니다. 08-6에서 구성별 합계를 비교합니다.

미리 말해 둘 것은, 토큰이 늘어난 만큼 정답률이 오르는지가 질문이지 토큰 자체가 문제는 아니라는 점입니다. 규정 문서 전체를 넣는 방식은 토큰이 더 많으면서 정확도는 더 낮을 수 있습니다. 08-6의 표는 그래서 정답률과 토큰을 나란히 놓습니다.

정리

  • 프롬프트에는 개념 정의, 근거 조항(유효기간 포함), 판단 결과(계산 과정·미확인 포함), 질문 네 가지만 넣습니다.
  • 원시 데이터와 관련 없는 정의는 넣지 않고, 답변의 모든 문장이 프롬프트 안에 출처를 갖게 합니다.
  • 사전 조회 방식은 재현성이 높아 비교 실험에 맞고, 도구 호출로 바꾸더라도 규칙 평가는 코드에 남깁니다.
