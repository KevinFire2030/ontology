09-1에서 그래프 탐색이 유리한 질문 유형을 정리했습니다. 이 절에서는 그 탐색을 PostgreSQL 안에서 하는 두 가지 방법을 봅니다. 재귀 CTE(Common Table Expression)는 표준 SQL이라 어디서나 되고, Apache AGE는 PostgreSQL 확장으로 그래프 질의 언어 Cypher를 쓰게 해 줍니다. 노트클라우드의 조항 링크 그래프로 두 방법을 시연하고 성능과 표현력, 함정을 비교합니다.

간선 목록으로서의 clause_links

6-3의 clause_links 테이블은 그 자체가 그래프의 간선 목록(edge list)입니다. from_clause가 출발 노드, to_ref가 도착 노드, rel이 간선 종류입니다. 노드 테이블을 따로 두지 않아도 clauses와 concepts가 노드 역할을 합니다.

refund_policy_v2:6.1 ──applies_mutatis_mutandis──▶ refund_policy_v2:3
                     ──applies_mutatis_mutandis──▶ refund_policy_v2:4
refund_policy_v2:4.1 ──supersedes────────────────▶ refund_policy_v1:3.1
faq:결제와 구독       ──cites────────────────────▶ refund_policy_v2:4.1
ops_manual:2         ──cites────────────────────▶ refund_policy_v2:4.1
                     ──cites────────────────────▶ terms_of_service:9.3
refund_policy_v2:2.1 ──defines───────────────────▶ concept:Unused

간선 56개, 종류 4개짜리 작은 그래프입니다. 작지만 09-1의 세 가지 질문 유형(다단계 추적, 영향 범위, 경로)이 모두 있습니다.

재귀 CTE: 정방향 탐색

"학생 요금제 6조 1항이 준용하는 조항과, 그 조항이 대체한 1판 조항"을 한 번에 찾는 조회입니다.

WITH RECURSIVE walk AS (
    SELECT from_clause, rel, to_ref, 1 AS depth,
           ARRAY[from_clause, to_ref] AS path
    FROM clause_links
    WHERE from_clause = :start AND rel = ANY(:rels)
  UNION ALL
    SELECT l.from_clause, l.rel, l.to_ref, w.depth + 1,
           w.path || l.to_ref
    FROM clause_links l
    JOIN walk w ON l.from_clause = w.to_ref
    WHERE l.rel = ANY(:rels)
      AND NOT l.to_ref = ANY(w.path)          -- 순환 방지
      AND w.depth < :max_depth
)
SELECT depth, rel, from_clause, to_ref, array_to_string(path, ' -> ') AS path
FROM walk ORDER BY depth, to_ref;

구조는 항상 같습니다. 첫 SELECT가 시작점에서 나가는 간선(깊이 1)을 고르고, UNION ALL 아래의 SELECT가 직전 결과의 도착 노드에서 다시 나가는 간선을 고르기를 반복합니다. path 배열에 지나온 노드를 쌓아 두고 이미 지난 노드로는 가지 않게 하면 순환이 있어도 멈춥니다. max_depth는 안전장치입니다.

실측 결과입니다.

== 정방향: 학생 요금제 6조 1항이 준용하는 조항과 그 조항이 대체한 1판 조항
  depth 1 [applies_mutatis_mutandis] refund_policy_v2:6.1 -> refund_policy_v2:3
  depth 1 [applies_mutatis_mutandis] refund_policy_v2:6.1 -> refund_policy_v2:4

== 정방향: 2판 4조 1항이 대체한 1판 조항
  depth 1 [supersedes              ] refund_policy_v2:4.1 -> refund_policy_v1:3.1

첫 조회에서 깊이 2가 나오지 않은 이유가 있습니다. 준용은 조 단위(4)로 걸려 있고 대체는 항 단위(4.1)로 걸려 있어서, 4에서 4.1로 내려가는 간선이 없습니다. 조와 항의 소속 관계(part_of)를 간선으로 넣지 않고 조항 ID의 문자열 구조로만 표현했기 때문입니다. 그래프 탐색을 제대로 하려면 이 소속 관계도 간선이어야 합니다. 09-3에서 이 점을 보완합니다.

재귀 CTE: 역방향 탐색(영향 범위)

"이 조항이 바뀌면 함께 점검할 것"은 간선을 거꾸로 따라가는 조회입니다. JOIN 조건만 뒤집으면 됩니다.

WITH RECURSIVE impact AS (
    SELECT to_ref AS target, from_clause AS dependent, rel, 1 AS depth,
           ARRAY[to_ref, from_clause] AS path
    FROM clause_links
    WHERE to_ref = :start
  UNION ALL
    SELECT i.dependent, l.from_clause, l.rel, i.depth + 1,
           i.path || l.from_clause
    FROM clause_links l
    JOIN impact i ON l.to_ref = i.dependent
    WHERE NOT l.from_clause = ANY(i.path)
      AND i.depth < :max_depth
)
SELECT DISTINCT depth, rel, dependent, array_to_string(path, ' <- ') AS path
FROM impact ORDER BY depth, dependent;

== 영향 범위: 2판 4조 1항(연간 30일 전액 환불)이 바뀌면
  depth 1 [cites   ] faq:결제와 구독               refund_policy_v2:4.1 <- faq:결제와 구독
  depth 1 [cites   ] ops_manual:2                 refund_policy_v2:4.1 <- ops_manual:2

== 영향 범위(조 단위 포함): 2판 4조
  depth 1 [applies_mutatis_mutandis] refund_policy_v2:6.1   refund_policy_v2:4 <- refund_policy_v2:6.1

== 영향 범위: 약관 9조 3항(유리한 규정 적용)
  depth 1 [cites   ] ops_manual:2                 terms_of_service:9.3 <- ops_manual:2

Q30의 답이 여기서 나옵니다. 4조 1항이 바뀌면 FAQ와 운영 매뉴얼 2절을 점검해야 하고, 4조 전체가 바뀌면 학생 요금제 6조 1항(준용)도 점검 대상입니다. 06-4의 impact_of 함수는 깊이 1만 보는 단순 조회였고, 재귀 CTE는 깊이를 늘릴 수 있습니다. 지금 그래프에서는 깊이 2 이상이 나오지 않는데, 간선이 56개뿐이고 인용이 한 단계로 끝나기 때문입니다. 세무 법령처럼 시행령이 법을 인용하고 예규가 시행령을 인용하는 구조에서는 깊이 3~4가 흔합니다.

Apache AGE: Cypher로 같은 것을

Apache AGE는 PostgreSQL 확장으로, 같은 데이터베이스 안에 그래프를 만들고 Cypher로 질의합니다. 집필 환경의 내장 PostgreSQL에는 AGE가 없어, 아래는 03-1의 Docker 경로에 있는 age 컨테이너(apache/age:release_PG16_1.6.0, AGE 1.6.0 / PostgreSQL 16.10)에서 실제로 실행한 결과입니다. 문법 설명은 공식 문서(https://age.apache.org/age-manual/master/intro/overview.html)를 따랐습니다.

-- 확장 활성화와 그래프 생성
CREATE EXTENSION IF NOT EXISTS age;
LOAD 'age';
SET search_path = ag_catalog, "$user", public;
SELECT create_graph('policy');

create_graph는 빈 그래프를 만들 뿐입니다. 관계형 테이블인 clauses와 clause_links는 자동으로 변환되지 않으므로, MATCH를 쓰기 전에 노드와 간선을 직접 적재해야 합니다. 최소 절차는 두 단계입니다.

먼저 조항을 노드로 만듭니다. clauses의 clause_id를 읽어 행마다 CREATE를 실행합니다.

-- 노드 적재 (조항 1건당 한 번)
SELECT * FROM cypher('policy', $$
    CREATE (:Clause {id: 'refund_policy_v2:4.1', doc: 'refund_policy_v2'})
$$) AS (v agtype);

다음으로 clause_links의 행마다 양 끝 노드를 찾아 간선을 만듭니다. rel 값을 간선 레이블로 씁니다.

-- 간선 적재 (링크 1건당 한 번)
SELECT * FROM cypher('policy', $$
    MATCH (a:Clause {id: 'faq:결제와 구독'}), (b:Clause {id: 'refund_policy_v2:4.1'})
    CREATE (a)-[:cites]->(b)
$$) AS (e agtype);

실무에서는 이 두 문장을 파이썬 루프로 돌려 테이블을 훑습니다. 간선 레이블은 Cypher 문 안에 상수로 들어가야 하므로 rel 값별로 문장을 나누어 만들고, 노드를 먼저 다 넣은 뒤 간선을 넣어야 MATCH가 실패하지 않습니다.

여기서 개수를 정확히 세어 두어야 합니다. clause_links 56행이 모두 조항 사이의 간선은 아닙니다.

관계 행 수 도착 노드
cites 28 조항
supersedes 13 조항
applies_mutatis_mutandis 2 조항
defines 13 개념 또는 속성 (concept: 접두어)

양 끝이 모두 조항인 간선은 43개입니다. 그래서 Clause 노드 108개만 만들고 모든 링크의 양 끝을 Clause로 MATCH하면 defines 13개는 짝을 찾지 못해 43개만 들어갑니다. 조항 관계만 실습한다면 defines를 빼고 기대값을 43으로 잡으십시오.

개념까지 옮기려면 한 가지가 더 있습니다. defines의 도착 노드 11종에는 concepts 테이블의 개념뿐 아니라 billing_cycle, paid_at, Seat 같은 속성 이름도 섞여 있습니다. concepts 22개만 노드로 만들면 속성을 가리키는 간선이 또 실패합니다. 속성도 노드로 만들거나(레이블을 Attribute 등으로 구분), 05-3에서 정한 대로 속성을 개념으로 승격해 모델을 정리한 뒤 옮기는 편이 낫습니다.

적재 후 개수가 이 값과 다르면 중간에 실패한 것이므로 count로 먼저 확인하는 편이 좋습니다. 실제로 108개 노드와 56개 링크를 넣어 본 결과입니다.

노드 적재 108개 / 0.4s
간선 문장 실행 56건 / 예외 0 / 0.2s
실제 Clause 노드: 108
실제 간선: 43
  cites: 28
  supersedes: 13
  applies_mutatis_mutandis: 2
  defines: 0

여기서 한 가지 주의할 점이 보입니다. defines 13건은 오류를 내지 않고 조용히 0개가 됐습니다. MATCH가 짝을 찾지 못하면 CREATE가 실행되지 않을 뿐 예외가 아니기 때문입니다. 적재 스크립트가 끝까지 돌았다는 것만으로는 다 들어갔다는 뜻이 아니므로, 반드시 count로 대조해야 합니다.

노드와 간선이 들어가면 영향 범위 조회는 다음과 같습니다.

-- 4조 1항을 가리키는 모든 것, 깊이 3까지
SELECT * FROM cypher('policy', $$
    MATCH p=(dep)-[*1..3]->(c:Clause {id: 'refund_policy_v2:4.1'})
    RETURN dep.id, length(p)
$$) AS (dependent agtype, depth agtype);

실행 결과입니다. 앞의 재귀 CTE가 낸 답과 같습니다.

"faq:결제와 구독"   1
"ops_manual:2"      1

4조 전체로 바꾸면 준용 관계인 학생 요금제가 나오는 것도 같습니다.

"refund_policy_v2:6.1"   1

ID에 공백이 들어간 faq:결제와 구독도 Cypher 문자열 안에서 그대로 매칭됩니다. 07-4에서 정규식이 이 ID를 잘랐던 것과 달리, 여기서는 값 전체가 하나의 문자열이라 문제가 되지 않습니다.

깊이를 돌려줄 때 length에 넘기는 것은 관계 변수가 아니라 경로 변수입니다. 가변 길이 패턴의 관계 변수(대괄호 안의 r)는 지나온 관계들의 목록이고, length는 경로의 길이를 구하는 함수입니다. 그래서 위처럼 MATCH 절에서 경로 전체를 p에 묶은 뒤 length(p)를 씁니다.

적재를 빼고 조회만 보면 재귀 CTE 20줄이 Cypher 3줄이 됩니다. 가변 깊이(*1..3), 방향, 순환 처리가 언어에 내장되어 있기 때문입니다. 다만 위에서 본 적재 비용이 그 앞에 붙습니다.

함정과 한계

  • 소속 관계를 간선으로 넣지 않으면 탐색이 끊깁니다. 위에서 본 조·항 문제입니다. ID 문자열에 구조를 숨기면 SQL로는 처리할 수 있어도 그래프 탐색에서는 보이지 않습니다.
  • 재귀 CTE의 순환 방지는 어떤 방식으로든 반드시 넣어야 합니다. 아무 장치 없이 두면 순환 그래프에서 무한 반복합니다. 이 책의 예제는 path 배열에 지나온 노드를 쌓아 두고 검사하는 방식으로 구현했습니다. PostgreSQL 16에는 같은 일을 문법으로 해 주는 CYCLE 절이 있어서, CYCLE to_ref SET is_cycle USING path 형태로 쓰면 순환 감지와 경로 배열을 데이터베이스가 만들어 줍니다(PostgreSQL 16 WITH 질의 문서). 직접 쓴 배열 검사는 다른 데이터베이스로 옮기기 쉽고, CYCLE 절은 짧고 실수가 적습니다. 어느 쪽을 쓰든 max_depth를 함께 두는 것이 안전합니다.
  • DISTINCT를 잊으면 같은 노드가 경로 수만큼 나옵니다. 영향 범위처럼 "무엇이 영향받는가"만 필요하면 DISTINCT, 경로가 필요하면 그대로 둡니다.
  • 간선 종류를 섞을 때 의미가 달라집니다. 준용 뒤에 대체를 따라가는 것과 대체 뒤에 준용을 따라가는 것은 다른 질문입니다. rels 목록을 넘길 때 어떤 순서 조합을 허용하는지 정해야 합니다. 이 책의 정방향 조회는 두 종류를 구분 없이 허용했는데, 규정 해석에서는 "1판 조항이 준용하던 것"을 2판에 적용하면 안 될 수 있습니다.
  • AGE는 데이터를 두 벌로 만듭니다. clause_links를 그래프로 복사하면 링크가 바뀔 때 둘을 맞춰야 합니다. 09-5의 판단 기준에서 이것이 "관리 부담" 항목입니다.

정리

  • clause_links는 그 자체가 간선 목록이며, 재귀 CTE로 정방향(준용·대체)과 역방향(영향 범위) 탐색을 실측했습니다.
  • 재귀 CTE는 설치 없이 되지만 순환 방지(path 배열 또는 PostgreSQL 16의 CYCLE 절)와 깊이 제한을 명시해야 하고, AGE는 Cypher로 짧게 쓰지만 확장 설치와 노드·간선 적재, 이후의 동기화가 필요합니다.
  • 조와 항의 소속 관계처럼 ID에 숨긴 구조는 그래프 탐색에서 보이지 않으므로 간선으로 넣어야 합니다.
